# P-001 对战模式（Arena）—— 皇室战争那种打法，但"以建筑为主、军队为辅"

用户原话（2026-10-27）：
> 这个模式不好玩……这个素材可以改成《皇室战争》和《部落冲突》的那种玩法……开一个新的文件。
> 对应的素材可以共用，但是逻辑全部不一样，这个主城就是核心。我们给 20 点金。
> 1. 底层随机给 4 张卡牌，也可以配卡组（稍后再做）。
> 2. 先把游戏动起来。双方头上的水晶，一方蓝一方红（对方红）。
> 要增加建筑和旗帜。优先"以建筑为主、以军队为辅"：先建建筑，再建军营；
> 军营自动出兵互相打，也可以直接召唤军队；充分用小像素人生成器做单位、平衡血量。
> 不同于皇室战争：咱们这边的建筑**不会自动掉血掉光**。

## 1. 打算改什么

**新开一个并行模式**，老模式一行不删（`index.html` 仍是抽卡 RTS，`arena.html` 是对战）。
- 新入口 `arena.html` + `src/arena/`（main / config / cards / ArenaWorld / ArenaApp / ArenaHud）
- 复用：`engine/*`（相机/渲染/输入/循环）、`game/models/*`（3D 建筑）、
  `game/dudes/*`（素材包/图集/像素小人/长相）、`ui/theme.ts`（木金材质）、`ui/dom.ts`
- 全新：金币、手牌、双方 AI、出兵与拆核心、旗帜集结点、HUD

## 5. 风险与代价

1. **第三次"重写玩法"**：老模式不是废案，两个入口并存；但用户很可能会只留一个。
   所以我把新模式的逻辑全部隔离在 `src/arena/`，删掉它不影响老模式。
2. **素材复用**：像素小人只有 1 个体型，蓝/红靠"衣服色带"区分（己方蓝带、敌方红带），
   这和 P-002 定的"自己人蓝、敌人随机"不同 —— 新模式要"敌我一眼分清"，所以**强制红带**。
3. **不做配卡组**（用户说稍后），也不做卡牌升级/宝箱/皇冠箱。
4. 旗帜这一层：军营的出兵点可点旗改位置（复用旗子袋那套手势），但一次只做"军营旗"。

### 追加：小人陷进地里 + 一堆 UI 错位（2026-10-27，用户截图反馈）

用户原话：「小人为什么总是只露半边身子，另一半身子陷在地里面……把它自动拉伸一下，拉长一点」
「这个地皮 UI 也有问题，UI 基本上都有问题」。

**根因（代码里量出来的，不是猜）**
1. 小人的脚从 y=0 起算，而草地表面在 y=0.5 —— 整只埋进去 0.49（身高 1.45 的一半还多）。
   老模式的 `UnitView` 一直有 `surfaceY + 身高/2` 这一句，我这一版漏了。
2. 建筑同理：模型说明书写明"局部原点在底面、底面 y=0"，我写成了 `position.set(..., 0, ...)`，
   应该抬到 `footprintSurfaceY`。老模式的 `BuildingView` 也是这么做的。
3. 手牌飘在屏幕正中间：`.ahud` 是 `space-between` 的三段，顶栏/手牌/提示被分别顶到上中下。
4. 桌面宽度下卡片被 `flex:1` 拉成 350px；地图按 45° 斜角转成菱形，四角全是黑洞；
   两颗核心共用同一套模型，只有头顶小水晶分得清。

**修法**
- 小人：`y = 地表 + UNIT_HEIGHT/2`，并把身高从 1.12 提到 **1.45**（等比放大，不拉扁）；没有素材包时的锥体同样抬。
- 建筑：`y = max(占地内各格地表)`。
- HUD：手牌+提示装进 `.ahud__bottom`（`margin-top:auto`），限宽 560 居中，卡面瘦到 62px。
- 相机：对战模式单独一档 `ARENA_CAMERA`，**yaw 0**（正对战场，蓝下红上），
  并按"整幅场地入画"现算缩放（横/竖屏分别算，取大者），竖直多留 4 格给手牌。
  场地四周加一块底盘，不再是黑洞。
- 核心：加一圈阵营色地环（蓝/红），水晶从 0.34 放大到 0.46。

**实测**
- 精灵中心 y = 1.225，身高 1.45 ⇒ 脚在 **0.5**，与草地表面完全一致（修前脚在 0.012，埋掉 0.49）。
- 截图三条（修前/修后）都在这一轮的实机画面里：手牌从屏幕中部移到贴底、地图从菱形变正对、
  双方核心红蓝可辨、单位脚踩地面有影子。

**没做**
- 单位再拉更长（现在 1.45 已经比老模式高 30%）。如果还要更高，改 `src/arena/config.ts` 的 `UNIT_HEIGHT` 一个数即可。

## P-002 横版场地 + 多视角 + 建筑动效（用户 2026-10-27 第二轮）

用户原话要点：横版（左我／右敌）、多视角且能自动移动、射击从塔顶出弹、炮塔转向（**后来更正：
"不是全自动转向"**）、风车要转、卡牌有时点不到、底部 tips 去掉；另外**建筑一律 3×3 占地并放大**、
**建筑要有破损**、**血条要放大**；**田里拖动=移动画布，黑色区域拖动=上下左右转视角**。

### 改动

| 件 | 改成什么样 |
| --- | --- |
| 场地 | 26×16 横版；`midCol=13`，蓝在左、红在右；核心 3×3 落在两端 |
| 占地 | **所有建筑 3×3**；模型统一放大 1.75 倍（`BUILDING_SCALE`） |
| 血条 | 每栋楼都挂（满血隐藏）、宽 2.6、高 0.2；挂在**反向缩放**的子组里，不会被放大 |
| 破损 | 三道深色裂纹，血量 ≤66% / ≤40% / ≤20% 依次露出 |
| 炮塔 | 不是常驻自动转向：只有开火那 0.18 秒里才朝 `aim` 摆过去（用户更正过"不是全自动转向"） |
| 射击 | 塔开火时从**塔顶**生成可见弹丸（箭 0.22s / 炮 0.45s，炮弹走高抛物线），命中仍即时结算 |
| 风车 | 磨坊改成自建件：石塔 + 锥顶 + 四片帆，帆绕 z 轴持续旋转（1.7 rad/s） |

| 手动 | 玩家一拖就**锁死手动**（不再 6 秒后偷偷抢回），按"视角"按钮才回到自动 |
| 拖动分流 | 起点在**场地内** = 平移；起点在**黑区** = 转视角（左右改 yaw、上下改 pitch，24°–78°） |
| tips | 底部提示整块删掉；换成右上角一颗"视角 · 全景"按钮 |
| 卡牌 | 卡面三块子节点只建一次（以前在 20Hz 刷新里 replaceChildren，手指按下那一帧被换掉 →
  这就是"有时候点不到"）；不再用 `disabled`，点不动时给一句原因 |

### 实测（真页面）

- 风车：`sails.rotation.z` 0.00 → −9.01（0.5 秒）✓ 在转。
- 炮塔：开火窗口里 `turret.rotation.y` −0.60 → −0.57，`aim=0.57`；`shotsMuzzle` 命中 3 帧。
- 弹丸：飞行中 `shotMeshes` 最多 1 个，落点后归零。
- 血条：磨坊 105/300 ⇒ 条可见、宽度 0.35、`y=2.5`（反向缩放生效，不再悬空）。
- 裂纹：0.35 血量 ⇒ 第 1、2 道可见、第 3 道隐藏。
- 拖动分流：黑区 pointerdown → `gestureFromField=false`，场地中心 → `true`；
  黑区拖 120×60 px ⇒ yaw 0 → 26.4°、pitch 52 → 41.2°；田里拖 ⇒ yaw 不变。

### 我自己在这一格犯的两条

1. **血条挂在被放大的组里**：跟着 1.75 倍放大 + 位置抬到 4.2，截图里是两条悬空横线。
   修法是加一层 `ui` 子组做 1/1.75 反向缩放 —— 也提醒我一件事：**位置坐标永远是"局部"的**，
   父级一缩放，所有硬编码的 y 都要跟着重算。
2. **黑区拖动被判成"在田里"**：我一开始只用"射线打到地面平面"当判据，
   但那条射线在场地外也命中（无穷大平面）⇒ 黑区拖动变成了平移。
   改成"命中点落在格子且该格子在地图内"。

## P-003 场地放大 + 中场分隔线 + 金币节奏 + 单位指挥 + 白嫖修正

| 项 | 改成什么 | 依据 |

| 白嫖修正 | 塔的射程改成**从占地边缘量**，和"兵打建筑按边缘算距离"同一口径 | 见下 |

### 白嫖那一格的根因（量出来的）

3×3 之后：兵是"贴到**边缘**"就开始打，塔却是"从**中心**量射程"。
炮塔 4.4 的中心射程只够到边缘外 `4.4 − 1.5 = 2.9` 格，
而弓箭手在边缘外 **3.6** 格就能打到它 —— 差 0.7 格，所以能站着白打整座炮塔。

修法：塔也按边缘量（`range + 半边长`）。修完复测（清掉 AI 的兵，只留 1 塔 + 3 弓手）：

| 场景 | 修前 | 修后 |
| --- | --- | --- |
| 3 弓手 vs 炮塔 | 弓手能站着打，塔掉血（不死的仗） | **弓手全灭**，塔还剩 598/640 |
| 3 弓手 vs 箭塔 | 同上 | **弓手全灭**，塔还剩 436/520 |

### 锁

新增两条：① 点地面 → 全军朝那儿走且到点后清空指令；② 站在塔边缘外 3.5 格的弓手
必须付出代价（掉血或死）。两条都先红过（夹具修正后才绿）：
- 第一条一开始断"塔能放下去"，而我把开局金从 5 提到 8 之后 7 费的炮塔变得买得起，
  旧锁"金不够不能出牌"因此变红 —— 改成先把金压到 2 再试。
- 第二条一开始直接读 `units[0].hp`，而弓手会被打死、数组被清空 → 改成"死了算过、掉血也算过"。

全量 **19 个文件 / 275 条**绿。

## P-004 阵营标识重做：石台 + 会飘的旗 + 模型台面配色

用户否掉了上一版做法："这个炮塔这样很明显是让我不满意的……你让他的那个台面上、
就是你看一下模型上的台面上有颜色，我们额外再准备一个旗帜，然后风车顶盖上的颜色是不同的，
我们再准备一个旗帜，有些地方可以放，比如炮塔上可以放一个飘动的旗帜。"

### 我原来错在哪

第一版是**在脚下贴了一块纯色方板**当地毯用 —— 那不属于模型的一部分，看着像铺了块布。
用户要的是"台面本身有颜色"。

### 现在的做法（新件 `src/arena/props.ts`）

1. **石台**（`makePlinth`）：底层深石（比占地略大）→ 上层阵营色台阶（收进半格）→ 一道亮色沿。
   三层叠起来才像"这栋楼立在一块刻着自己颜色的石台上"。
2. **会飘的旗**（`makeBanner`）：一根杆 + 分 7 段的布。布面每帧按 `sin` 位移顶点
   （两个频率叠加，越靠旗尾摆幅越大），不用着色器。
   - 杆高必须 **高过屋顶**：模型放大 1.75 倍后屋顶约 2.8，杆矮了整面旗都会被楼挡住
     （第一版就是这样，旗子"有但看不见"）。
   - 位置放在石台四角：核心/箭塔左上，磨坊/炮塔/兵营各选一角。
3. **模型台面配色**：磨坊顶盖、炮塔台面按阵营上色（`shade(sideColor, 0.75~0.9)`），
   这样即使不看旗子，也能一眼分出谁是谁的。

### 实测

- 旗子数量：8 栋楼 → 8 面旗（`parts` 里每个都带 `banner`）。
- 布面在摆：同一面旗 t=1.0 与 t=2.0 的顶点数组不同（第 6 个顶点的 z 从 −0.0101 → −0.0123，
  第 9 个从 −0.0095 → +0.0023），确认是**逐顶点**在动，不是整块平面转。
- 炮塔朝向：蓝 `aim=0`、红 `aim=π`（互相瞄准），渲染后 `turret.rotation.y` 分别是 0 / −3.14。

### 一个量具上的教训（我自己的）

验证"布面在摆"时，我用"遍历组里第一个顶点数 >10 的 Mesh"去抓旗面 ——
抓到的其实是**石台的方块**（BoxGeometry 24 个顶点），两次读数完全一样，差点判成"没在动"。
改成按 `geometry.parameters.widthSegments === 7` 抓，才拿到真旗面。
⇒ 抓对象要按**它区别于别的东西的特征**抓，别按"看起来差不多"的尺寸。

### 追加：随机碎裂（废墟长得不一样 + 塔受伤掉渣）

- 新 `src/arena/ruins.ts`：**递归二分切块（BSP）** —— 从占地矩形开始，每次挑一块最大的、
  随机挑轴（长边 72% 沿长边切）、随机比例（32%–68%）切一刀，递归到够块数。
  切出来的块互不重叠、拼起来正好覆盖原地，所以像"这栋楼碎成了这些块"。
  - **确定性**：只由 (seed + 楼号) 决定 ⇒ 同一堆废墟刷新前后一样，不同楼必然不同。
  - `fracture(cols, rows, seed, n)` 给废墟；`spall(...)` 把其中几块推到墙外、压小，给"掉渣"用。
- 废墟渲染：每块按来源（屋瓦 / 墙体 / 木梁）取不同色族，随机转向、随机高度、随机明度；
  出现后前 0.5 秒"从中心炸开再落定"，之后静止，14 秒到期淡出。

#### ⑥ 追加：帆错位 —— 布没贴在木梁上（用户 2026-10-28）

用户原话：「我希望他的帆错位了……他明明应该紧紧贴着那个木棍的，就在那个木棍后面」。

**根因（几何算出来的，不是猜）**：套件的语义是 `at` = 绝对模型坐标、`rot` = **绕自身中心**转，
带 `spin+pivot` 的件由套件建一个位于 pivot 的 Group 绕轴心公转。
而上一版四片布的**位置是我手算的散点** —— 例如 `[0.2, 2.02]` 相对轴心 (0, 1.62) 的方向是 **63°**，
梁长轴却是 **45°**。**布和梁不同向**，于是帆飘在棍子旁边（实测方向偏差 **71.57°**）。

修法：按梁的方向线摆 —— 绕 z 转 θ 的竖直长条长轴方向是 90°+θ，
所以布心也落在同一条方向线上（±cos45 分解），布自身的 rot 与梁同值：
- `ALONG = 0.47 × cos45 = 0.332`（布长 0.78 ⇒ 覆盖 0.08~0.86，正好铺满 0.85 的臂）；
- `CLOTH_Z = 0.72`：梁厚 0.05、中心 0.76（占 0.735~0.785），布厚 0.03 ⇒
  布的前表面落在 0.735，**正好抵住梁的背面**（镜头在 +z，所以布藏在木棍后面）。

**锁（3 条，339 条全绿）**：两根梁 + 四片布挂同一轴心 / 每片布的方向角对齐自己的梁（模 180）/
布的 z 比梁小但差 ≤0.07（贴着，不是穿过去也不是悬空）。
变异检查：把布改回 `[0.2, 2.02]` ⇒ 方向偏差 71.57°，锁立刻红；还原即绿。

### P-020 追加：弹丸加尾巴（2026-11-02）

用户原话：「攻击可以更明显一些吗？我这边就是觉得这个射出的炮弹还有箭矢，要不给他们后面加一个尾巴」。

#### ① 为什么用几何体，不用粒子

`BattleFx` 的烟池上限 64 团。一场仗同时几十发弹在飞，每发再抽 5 团烟去当尾巴，
池子当场见底 —— 后面的弹丸就没尾巴了（这跟"工地雾吃满 72 团、后面工地一团排不上"是同一个坑）。
所以尾巴是**跟着弹丸走的一根锥**：不采样轨迹、不占池子，代价只是每次开火 +1~2 个 draw call。

| 弹种 | 尾巴 | 朝向约定 |
| --- | --- | --- |
| 箭 | 细锥 0.04 × 1.05（米白，opacity 0.42） | 箭沿 +Z 飞 ⇒ 锥 `rotation.x = +π/2` |
| 炮弹 | 浅灰烟锥 0.15 × 1.25（0.24）+ 亮橙尾焰锥 0.06 × 1.0（additive 0.62） | 沿 +X 飞 ⇒ `rotation.z = -π/2` |
| 法术弹 | 青锥 0.085 × 0.95（additive 0.55） | 同上 |

几何体与材质**全场共用**（`TRAIL_GEO` / `TRAIL_MAT`），所以移除弹丸时那段 dispose 必须跳过它们
（`mesh.userData['trail'] = true`）—— 否则第一发炮弹落地就把后面所有炮弹的尾巴几何销毁了。
写这条的时候特意回头核对了原来那段 dispose：它只 dispose 炮弹/法术弹的几何（箭是共享的），
尾巴正好也落在"炮弹"这一支里，不跳过就会踩雷。

#### ② 调了三轮，都是看截图调的

| 轮 | 结果 | 问题 |
| --- | --- | --- |
| 1 | 深黑烟锥 0.17 × 0.95 | 在绿草地上是**一根看不见的灰棍子** |
| 2 | 加长到 1.45、半径 0.19 | 变成**黑柱子**，末端比弹丸还粗，像一根胡萝卜 |
| 3 | 0.15 × 1.25 + 橙色内焰 + 烟改浅灰 0.24 | 三条尾巴都认得出来 |

实测（真页面，无头 Edge + CDP）：

- `tools/shot_trail.js`：三行 × 三发（箭/炮弹/法术各三发，t=0.2/0.45/0.7），
  九发同时在飞时尾巴仍然分得清 —— 见 `docs/shot-trails-20261102.png`。
- `tools/battle_shot.js`：真实战场（塔 + 兵营 + 兵 + 阴影）里抓到飞行中的箭，尾巴清晰可见。

#### ③ 没动的

- 炮弹走抛物线，但尾巴只按**水平方向**旋转（`rotation.y`），所以上升段尾巴是"平"的。
  弧高只有 0.9 格、仰角约 15°，屏幕上看不出来；真要跟着切线走，得在 `syncShots` 里算
  `d(arc)/dk` 再把尾巴单独俯仰一次 —— 等它真的碍眼再说。
- 老模式（`/`）的箭没动：这一轮只改对战模式。

### P-021 追加：黄区加宽、建筑要盖几秒、墙塌得更乱（2026-11-02）

用户原话（三件事一起说）：

> 「第一个，中间的那个黄色区域是不能建建筑的，而且那个区域可以再大一点。为什么敌方的建筑可以直接建到黄色区域。
>  第二件事情，这个建筑建起来是要时间的。建筑建起来的时候，我想着有几个脚手架，建筑慢慢升起来，
>  咱们在外面做的那个破损墙壁刚刚好可以派上用场，那个墙壁就慢慢地凭空垒上来了。学习箭塔，把炮台还有别的建筑也做一下。
>  还有到时候被破坏坍塌的那个墙，可以倒塌得更丰富、更有趣一些。那个砖头好像落到地上之后并不会倒下来，而是直直地插在地上。
>  实际上，它们可以有更趣味的物理效果：1. 如果受到类似于弓箭和砍的伤害，正常掉下来。2. 如果是炮击，可以炸散开。」

#### ① "为什么敌方的建筑能建进黄区" —— 逻辑没违规，是模型比占地宽

先量（20 个 seed、441 栋楼）：**压进禁建带的建筑 0 处**。落格判据一直是严的。

他看到的其实是：

- 建筑占地统一 3×3，但**模型比占地宽** —— 兵营 3.6 格、炮塔 3.6 格、大本营 4.0 格；
- AI 的落点原本是"黄区右沿 + 1 格"，一栋落在 col 24 的兵营，模型左边缘正好伸到 23.7 —— **压进黄区 0.3 格**。

所以做了两件事：**黄区 5 列 → 7 列**（`NO_BUILD.halfWidth` 2 → 3），
AI 落点再往外让一格（`margin = halfWidth + 2`）。现在贴着黄线也看不出"楼压进黄区"了。

副作用（**要记住**）：两边最近的合法落点相距 10 格，而箭塔边缘射程只有 6.8 ——
**跨中线"塔打塔"在实战里已经打不到了**。原来那条锁写的是"两座塔都在射程里时会互相拆"，
现在改成"塔会打进入射程的敌方建筑"（用 `instant` 把红方兵营摆进蓝塔射程造场景）。
要恢复塔互殴，得把射程提到 10.5 以上，那是另一件事。

#### ② 建筑要盖几秒

逻辑层（`ArenaWorld`）：

| 件 | 改成什么样 |
| --- | --- |
| `ArenaBuilding.build` | 新字段 0 → 1。`playCard` 落下去是 0，核心是 1 |
| `tickBuildings` | 每帧按 `BUILD.seconds[kind]` 推进；**没到 1 就 continue** —— 塔不开火、兵营不出兵、磨坊不生金 |
| `staffedIds` / `missingLogistics` | 只算 `build >= 1` 的楼：**施工中的楼不抢民居名额**（还没干活的楼凭什么让兵营停工） |
| `BUILD.seconds` | 民居 2.2 / 磨坊 2.8 / 箭塔 3.4 / 炮塔 3.8 / 兵营 4.2 |

视图层（`ArenaApp`）：

- **脚手架**：四角立柱 + 三层横梁 + 正面斜撑，材质全场共用；高度跟着 `build` 从 32% 长到 100%，
  完工后 0.25 秒缩没（不是"啪"地消失）。
- **楼体往上长**：`group.scale.y = build`（原点在底面）。**刻意没用"从地下升起来"**：
  位移露出的是屋顶（先看到顶、墙反而藏在土里），读起来像"楼掉坑里了"；压扁是"矮墙在长高"，才是垒墙。
- **墙慢慢垒上来**：`WallShell.setBuild(frac)` —— 面片在 rebuild 时按 y 从低到高排好，
  施工时用 `geometry.setDrawRange` 截断前 N 块。**不重建几何**：施工那几秒每帧重建 50 块
  BoxGeometry 会掉帧，drawRange 是零成本。
- 施工中不挂旗（父级 y 缩放会把旗压扁）、不显示"缺后勤"牌（同理会糊）。

#### ③ 墙塌得更乱：按伤害类型分两种死法

`hurtBuilding(b, attack, kind)` 多了一个 `HitKind`（`blade | arrow | cannon | magic`），
塔开火按塔种类定、单位按 `projectile` 定（近战 = blade、法师 = magic、弩车 = arrow、移动火炮 = cannon）。

| | 刀砍 / 箭射 | 炮弹 |
| --- | --- | --- |
| 初速度 | 顺着墙面法线 0.5–1.4 | **全方向** 1.6–4.0 |
| 上抛 | 0.9–2.2 | 1.8–3.6 |
| 翻滚 | ±8 rad/s | ±18 rad/s |
| 落地姿态 | 平躺 ±0.2 弧度 | 炸翻 ±0.7 弧度 |

落地那一行改了：`rotation.set(-π/2 + tiltX, yaw + yawJitter, tiltZ)`，每块都有自己的倾角。
上一版统一 `(-π/2, yaw, 0)` —— 一排板子躺得像铺地砖，薄板正对镜头时只剩一条线，
玩家就读成"砖头直直插在地上"。

**废墟**（整栋拆掉后那堆）也一起改了：

- 9 块 → 11 块，其中**前两块做成立着的断墙**（薄、高、歪 3–8°）。全平铺的方块像一堆地砖，
  没有"塌了一半的墙"这个剪影。
- 摊开方向原来是 `home + burst*(1-ease)` —— 从外侧**吸回**原位，读起来像倒放；
  现在是 `home + burst*ease`，从原位向外摊。幅度 0.6 倍（0.85 试过，散成一圈砖）。

### P-022 追加：碎块会自己消失、近战/远程两种粒子（2026-11-05）

用户原话：

> 「废墟砖块掉到哪里都不影响，只要最后过一段时间后自动消失，慢慢消失就可以了，
>  然后其他关于子弹拖尾。攻击有粒子效果，近战和远程都有不同的粒子放射。你可以帮我处理一下吗」

#### ① 碎块：从"永远躺着"改成"落地 12 秒后缩没"

先确认现状：**废墟**（整栋拆掉那堆）本来就有寿命 —— `RUIN.seconds = 14`，最后 2.5 秒按 ttl 淡出。
真正不会消失的是 `damage.ts` 里的**墙板碎块**：它们只在超过 `MAX_DEBRIS = 70` 时回收最老的，
也就是说打满 3 分钟，塔脚底下会积一圈永远躺着的板子。

改法：

| 项 | 值 |
| --- | --- |
| 寿命 | 落地后 **12 秒**（`DEBRIS_LIFE`） |
| 消失方式 | 最后 **2.2 秒**（`DEBRIS_FADE`）缩到 2% + 下沉 0.4 格 |

**为什么用缩小下沉而不是淡出**：碎块的材质按颜色共享（`matOf`），改 `opacity` 会把场上
所有同色碎块一起变透明 —— 一块到期，全场的墙板跟着变淡。缩小只动自己的 `scale`，安全。
顺带 `update` 改成倒序遍历（正序删元素会跳一块）。

#### ② 粒子：近战补上，远程按弹种分三档

分工先说清楚，避免重复：

| 谁 | 特效 | 从哪来 |
| --- | --- | --- |
| 近战（刀砍） | 闪光 + 6 颗（重击 8 颗）大号火星 + 一小团土 | **新增** `world.hits` 事件 → `fx.melee()` |
| 箭 | 2 团烟 + 3 颗火星 | `impact`（弹丸飞到目标时） |
| 法术 | 3 团烟 + 5 颗青点 | 同上 |
| 炮弹 | 7 团烟 + 10 颗火星 | 同上 |

- `ArenaWorld` 加 `hits` 队列（ttl 0.08，和 `heals` 同一套模式），**只上报近战**：
  远程有弹丸、视图在弹丸落地时自己放 `impact`，再报一次就是双重特效。
- `BattleFx.melee()` 的位置往**攻击者那侧退 0.45 格**：受击点正好压在像素小人的卡片上，
  小人是 alphaTest 0.5 的不透明面片，粒子生成在它正中心会被整块挡住
  （第一版截图里"只有脚下两粒白点"就是这个原因）。
- 给 `spark` 加了两个参数：`sizeScale`（近战用 2.2 倍）和 `lift`（上抛强度，近战 0.35）。
  默认的 `lift = 1` 是给"墙崩落往上溅"用的，近战那样会变成**头顶冒星**。
- 顺手删掉 `ArenaApp` 里炮弹落地时又补的 8 颗火星（现在 `impact` 按弹种自己放）。

#### ③ 实测

- 三对兵贴脸互砍，同一帧抓到 `hits = 6`、`sparks = 42`（截图 `docs/melee-sparks-20261105.png`）。
- 诊断读数：火星 sprite 在 [10.61, 1.54, 8.98]、scale 0.28 格、opacity 0.92、挂在场景里 ——
  确认**在渲染**（之前看不出，是柔光贴图叠在红骑士的黄色装饰上了）。
- `tools/battle_shot.js` 顺手修了一处：它用 `place` 建的塔现在是**施工中**的（`build = 0`），

### P-024 追加：音效与震屏（2026-11-05）

用户："这个声音、振频，这些感官上的，你可以帮忙处理一下吗……比如说建筑落地的时候有木材堆放的声音，
炮塔攻击还有军队冲锋也有声音，看看能不能用 API 或者下载一些东西来处理一下。"

#### ① 决定：**全部现场合成，一个音频文件都不加载**

不动用下载/素材 API 的三个理由：

1. 这是像素小人 + 低多边形的战场，合成音的音色反而更贴，采样音会"太真实"而脱节；
2. **零版权风险** —— 上架素材要过审，来源不明的音效是常见驳回点；
3. 零加载、包体不涨（`dist` 现在 0.7MB），而且每条音效都能带随机音高/时长，
   几十次开火不会听出"同一段录音循环"。

代价是"木材堆放""人声冲锋"这类靠采样才像的声音做不像。所以换了做法：
**不去模仿一根木头的录音，而是用五六声错落的短敲去表达"一堆木头放下去了"**。

#### ② 音效清单与实测峰值（这一列是量出来的，不是估的）

`tools/audio_probe.js` 在 master 后并一个 AnalyserNode，逐个播一遍读时域峰值：

| 音效 | 触发点 | 峰值 |
| --- | --- | --- |
| collapse | 建筑被拆 | **0.204**（最重） |
| cannon | 炮塔/火炮开火 | 0.185 |
| lose | 失败 | 0.128 |
| build | 施工完工（木材堆放） | 0.125 |
| impact | 远程命中 | 0.108 |
| win | 胜利 | 0.100 |
| place | 出牌 | 0.098 |
| melee | 近战命中 | 0.086 |
| kill | 单位阵亡 | 0.086 |
| coin | 金币到账 | 0.068 |
| arrow | 弓/弩开火 | 0.065 |

`silent: []` —— 11 条全部有声（第一版 melee 0.033、coin 0.025 偏轻，抬过一档）。

#### ③ 三层保障

1. **节流**：同名音效 45ms 内不重复（几十个兵同一帧命中，叠起来就是噪音）。
2. **压缩器**：master 后串 `DynamicsCompressor`（-12dB / 8:1）。这不是音质装饰 ——
   一场混战里近战 + 命中 + 阵亡可能同一帧响七八下，不压直接削波爆音。
3. **降级**：没有 `AudioContext`（node 单测、用户禁音频、iOS 静音）时
   `play()` 静默返回，一个异常都不抛（`tests/audio.test.ts` 钉住）。

解锁时机只有一个：开始菜单的**"开始对战"**点击 —— 浏览器只认用户手势。
菜单上那个"音效：开/关"也顺手解锁并放一声，玩家立刻知道开没开。

#### ④ 震屏（用户说的"振频"）

`CameraRig.shake(strength)`，三条设计：

- **只平移视点、不改角度**：正交俯视下这读作"地面被震了一下"；改角度会变成"镜头被拽了一把"，那是另一种手感。
- **取最大值不累加**：三发炮弹同时落地，累加会把镜头甩出去，取最大只是"这一下很重"。
- **3.2/秒 衰减**：约 0.3 秒，正好是一次打击的手感长度。

用量：建筑完工 0.16、建筑被拆 0.55。炮击命中暂未单独加（`impact` 太频繁，会变成持续抖动）——
真要做应该按"距离镜头远近"加权，而不是每发都震。

#### ⑤ 触发点

| 事件 | 位置 |
| --- | --- |
| 出牌成功 | `placeBuilding` 里 `selectedSlot = -1` 之后 |
| 施工完工 | `syncBuild` 的 `!info.built` 分支（本来就有这一帧的钩子） |
| 建筑被拆 | `syncBuildings` 的删除分支 |
| 阵亡 | `syncUnits` 的删除分支 |
| 开火 | `syncShots` 里"新弹丸出现"那一帧（`muzzle()` 旁边） |
| 命中 | `syncShots` 里弹丸消失那一帧（`impact()` 旁边） |
| 近战 | `syncHits`（和粒子同一个入口） |
| 金币 / 胜负 | `audioCues()`，每帧比一次上一帧（世界层不报这两件事） |

#### ⑥ 我没法验证的部分

**我听不到声音。** 探针只证明了"链路通、有信号、不静音"，
音色好不好、木材堆放像不像、混战时会不会太吵 —— 这些只能你自己开一局听。
参数都集中在 `src/audio/sfx.ts` 的 `voice()` 里，每个配方一小段。

### P-025 追加：人口 / 面包（容器）+ 卡面图标（2026-11-05）

用户原话：

> 「UI 栏目可能还需要面板和人口按钮，卡牌更漂亮一点，每个卡牌有 svg 图片，他们的下方，

#### ① 规则（就按他说的，只补了两处他没提的）

| 东西 | 效果 |
| --- | --- |
| 民居 | **+2 人口上限**，自己不占人口（它就是容器） |
| 磨坊 | **+2 面包上限**，占 2 人口（要人干活） |
| 塔 / 兵营 | 占 2 人口 |
| 每个兵 | 占 1 人口 + 吃 1 面包 |
| 开局 | 人口 0/6、面包 0/3 |

两处他没说、我按"能玩"补的：

1. **民居不占人口**。按字面"建筑减两人口"套到民居上就是 +2−2=0，人口永远不涨 —— 它会变成一座没用的楼。
2. **判定要"先加容器再看占用"**。6/6 满的时候如果连民居都盖不出来，人口就永远回不去了（死锁）。

#### ② 一个必须补的漏洞：兵营自己出兵也要吃

第一版只在 `playCard` 里查容量，跑 12 局立刻出问题：**人口 11/8、13/12**（超员）。
因为兵营每 6 秒自己吐一个兵，那条路根本没经过 `playCard`。

补上之后不再超员，而且**面包终于开始被消耗**（在此之前占用率只有 41%，因为兵都没出几个）。

#### ③ 实测（12 局 × 180 秒，每 10 秒采样一次，203 个样本）

| | 占用率 | 满员时间占比 |
| --- | --- | --- |
| 人口 | **77%**（6.9/9.0） | **28%** |
| 面包 | 37%（1.7/4.5） | 2% |

结论：**人口是主闸，面包目前只是副闸**。`baseBread` 试过 2 / 3 / 4：

- **2** → 面包 20% 时间满，有存在感，但**连一队 3 人弓箭手都放不出来**（3 > 2），开局寸步难行；
- **3** → 能出 1 队弓箭手，面包基本不卡（2% 满）；
- 4 → 33% 占用、3% 满，等于没有。

取 3。要让面包真正成为第二道硬闸，得改成"按卡算面包"或者提高每个兵的口粮 —— 那是另一笔。

#### ④ 副作用：节奏变慢，拆楼从 3.0 掉到 1.7

| | 施工前 | 加施工后 | 加容量后 |
| --- | --- | --- | --- |
| 平均拆楼/局 | 3.9 | 2.6 | **1.7** |
| 结束率 | 12/12 | 24/24 | 24/24 |

24 局：蓝 10 胜 / 6 负 / 8 平。平局变多是因为双方都拆不掉几栋。
**这是"限制建造"的直接代价**，要不要放松（比如 `basePop` 6→8）得用户定。

#### ⑤ 卡面：14 张内联 SVG

`src/arena/cardIcons.ts`，24×24、`currentColor`、只做剪影级设计（62–78px 高的卡上图标只有 26px，细节全丢）。

两个图标返工过：

### P-026 追加：竞技场围墙与看台（2026-11-06）

用户："给这个两边和后方加一个墙壁，和一个侧面有看台。面向玩家的就是两个面，

#### ① 先搞对了"后方在哪"

第一版把后墙放在 `z = rows`（第 20 行外侧）—— 结果它出现在**屏幕下方**，
把战场近侧切掉了一条。原因很直接：**相机站在 +z 往后退**，所以 z 越大离镜头越近。

正确布局：后墙 + 后看台放在 `z ≈ -0.4`（屏幕上方），左右墙在 `x = ±0.4`，

墙上百个盒子（含垛口）如果各自成 Mesh 就是上百次 draw call。这里按材质烤成一张几何体：
**墙 / 看台 / 座位 / 旗杆**各一次。看台是三级台阶（高 0.52、深 1.0），每级顶上一条深色坐板。

#### ③ 顺手抓到一个真 bug：**`bake()` 把"隐藏面"抹掉了**

`openBox` 用六面材质数组把朝外那面换成 `visible: false`，但 `bake()` 只抄

命中就 `continue` 跳过。**几何体里真的没有那些三角形**，不是靠材质骗过去的。

### P-029 追加：看台**整段**随镜头显隐（2026-11-06，用户澄清）

用户把上一版的"隐藏面"纠正了：

> 「看台的消失是这个意思，就是面向我们玩家的面的那个看台会自动消失，
>  比如说玩家在左边，那左边的看台就消失，玩家就是面对的是右侧那边，
>  然后右侧的看台就消失，左侧又重新显示出来。」

#### ① 之前理解错了

上一版做的是"把盒子朝外的那个面不渲染"（剖视）。用户要的是：
**离镜头最近的那一整段看台（台阶 + 座位 + 帆布 + 撑杆）整段 `visible = false`**，
镜头转过去之后它再回来、换成另一侧消失。

#### ② 实现

`stand.ts` 把几何按段分成 4 个 Group：`common`（墙 / 垛口 / 四角塔）、
`stand-back`、`stand-left`、`stand-right`。每段单独 bake，于是可以一键显隐。
墙和角塔很矮、不挡视线，留在 common 里始终显示。

`buildStand()` 返回 `ArenaStand { group, update(yaw), hidden }`，
`ArenaApp.draw()` 每帧喂 `rig.yaw`。

判据 `nearestSegment(yaw)`（**纯函数，单独测**）：

| yaw | 相机在 | 隐藏哪段 |
| --- | --- | --- |
| 0 / 360 / ±30 | +z（前方） | `front` —— 近侧本来就没建看台，三段全显示 |
| 45–135 | +x | `right` |
| 135–225 | -z | `back` |
| 225–315 | -x | `left` |

yaw=0 时相机在 +z；90 在 +x；180 在 -z；270 在 -x（和 `CameraRig.place()` 的
`sin(yaw)` / `cos(yaw)` 对得上）。`update` 里缓存上一次的段，只在切换那一帧改 `visible`。

#### ③ 实测

| yaw | `stand.hidden` |
| --- | --- |
| 0 | `front`（三段都在） |
| 90 | `right`（红白帆布那段整段消失） |
| 270 | `left`（用户举的第一个例子） |

默认机位（不动镜头）读数是 `front`，所以一打开游戏看到的还是完整竞技场；
**拖镜头转到侧面**才会看到对应那段整段消失。

#### ④ 锁（5 条新增，392 全绿）

四个方位各自的判据、负角度、以及"四个象限各只藏一段、边界不重叠"。

#### ③ 真病灶与修法

`mill` 卡全程只在手牌待 **89 帧**。旧判据 `mills < barracks`：没兵营时 `barracks=0`

- `draw()` 后勤保底遍历**所有缺口**（手上已有第一张就补第二张）；
- `reroll()` 保所有缺口，且**永远仍保一张房屋**（用户原话不破）。

## P-063 空中单位：机头朝向 / 高度体型 / 攻城车前置（2026-11-07 中午）

用户："首先是滑翔机，它甚至头没有对前，是歪过来滑的。然后是飞行高度，

尤其是热气球可以更大一点。哦，对了，移动火炮和移动弓弩，也是需要建造工厂才能后置使用。"

### ① 机头朝向（真 bug，不是手感问题）

`syncUnits` 的 `entry.flying` 分支**只设了 `rotation.z`（侧晃），从来没设 `rotation.y`**
⇒ 机体恒朝局部 +Z，而 `u.aim = atan2(dz,dx)` 里 0 是往 +X 走，于是整架横着漂。
攻城车看起来"没这个问题"是因为它的车头本来沿 **+X** 建（炮口 x=+0.72），
所以用 `rotation.y = -aim`；飞行模型前方是 **+Z**（前桨 z=+3.95、燕尾 z=-3.8），
要的是 `π/2 − aim`。两个前向轴差 90°，抄错就歪。
公式抽成 `flyers.ts` 的 `flyerYaw(aim)`，开局 `makeFlyerUnit` 也先给一次，
免得出兵那一瞬间闪一下歪的。

### ② 高度与体型（`FLYER_STYLE` 一张表）

| 项 | 原来 | 现在 |
| --- | --- | --- |
| 离地高度 | 1.25 格（比民居 3 格还矮，俯视像贴地滑） | **2.6 格** |
| 热气球 scale | 0.85 | **1.35**（涨最多，用户点名） |
| 空气螺旋机 | 0.80 | **1.05** |
| 扑翼轰炸机 | 0.34（翼展约 3 格） | **0.45**（约 4 格） |
| 贴地影子 | 一律 1.0×0.75 | 按机型放大，气球 1.5 |

高度与体型集中在 `visuals/flyers.ts` 的 `FLYER_STYLE`，`ArenaApp` 只读它，
不在三处各写一个数。探针实测三架 `rotation.y` 全 1.5708（aim=0 朝 +X）、
高度 3.0 / 3.06 / 3.15、scale 1.35 / 1.05 / 0.45。

### ③ 攻城车并入工厂前置

`TECH.flyerCards` 名字已经不覆盖了 ⇒ 改名 **`factoryCards`**，
收齐 `balloon / airscrew / bomber / mobileCannon / ballista` 五张；
`techHint` 文案改「需要齿轮工厂解锁空军与攻城车」。判据仍只有 `techAllows` 一处。

### ④ 一条测试变红 → 先归因，别改期望糊过去

加前置后 `tests/pve_20261107.test.ts` 的「托管蓝方守满一关 ⇒ win」变成 lose。
反证：把两张攻城车从 `factoryCards` 拿掉 ⇒ 立刻 win，确认是这次改动引起。
但**12 局 A/B 统计**：改动前 10 胜 2 负、改动后也是 10 胜 2 负 ——
是 `draw()` 候选池少两张导致 rng 序列整体偏移、单 seed 胜负互换，
**不是教学关变难**（和 P-061 那个坑同源）。
处理：给那条确定性锁固定 `seed: 2`（仍能 win/waves），另加一条
「托管蓝方 12 局至少守住 8 局」统计锁兜底，防止以后靠挑 seed 掩盖真退化。
