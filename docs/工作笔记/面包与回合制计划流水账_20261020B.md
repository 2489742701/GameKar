# P-005 ~ P-009 面包 · 岗位 · 三塔 · 回合 · 弹丸特效（2026-10-20 第二批需求）

用户原话拆成的判据（逐条对上，别漏）：

1. 新增**磨坊**与**田地**；**田地只能贴着磨坊盖**。
2. **磨坊产面包**；**主城默认给一些面包**。
3. **一栋小房屋要 1 个面包**，**一栋小房屋 +4 人口**。
4. **面包不够 → 提示"房屋造不出来"**。
5. **人口不够 → 给提示，但塔楼照样能造**；塔顶冒**人口小头像 + 打叉**；
   **缺员的建筑不能攻击，兵营同理**（不产兵）。
6. 三座塔：**箭塔 / 炮塔 / 魔法塔**，**装填速度与伤害各不相同**，**都有弹药设计**；
   魔法塔**速度特别快、伤害低、要 2 人口**；塔楼**能升级**，**魔法塔升级最贵**，**升级不占抽卡**。
7. 点塔 → 头顶弹**「升级」「拆除」**；**拆除要二级确认**。
8. **箭塔弹药 = 2D 的箭**；**炮塔弹药 = 3D 黑色方块**，落地**爆炸**；开火有**火焰感** + **像素风烟雾**。
9. **水晶获取、人口计算、其他结算都按回合**：敌人进攻 = 回合开始，进攻完 = 回合结束 → **财富自动入账**；
   下一回合有**准备时间**，**准备时间内水晶不涨**。
10. **面包与人口是"容积"不是每回合增加**：战斗中房屋被大量摧毁 → 人口掉到不够驱动兵营，
    但**本回合兵营照常产兵**（回合没结束、没结算）；**结算之后**人口才掉下去，玩家必须抽到房屋才补得回来。

## P-005 面包资源 + 田地 + 磨坊 + 房屋吃面包

**改什么**：`config.ts` 加 `bread` 资源与 `BREAD` 常量；`buildings.ts` 加 `mill`/`field`、
民居 `populationCap: 3 → 4`、民居 `cost.bread: 1`；`cards.ts` 补两张卡（磨坊 rare / 田地 common）；
`GameWorld` 加面包容积与"田地贴磨坊"的邻接判定。

**根据的读数**：民居现在 `populationCap: 3`、`cost.gold: 45`；`inspectPlacement` 的闸门顺序是
边界→地形→占用→唯一→许可→成本→人口（本轮要把最后一条挪走，见 P-006）。

**会动到哪一面**：会改答案 —— 民居人口上限 3→4 是**他指定的**；`data.test.ts` 里若钉着 3 要改口（列在下面"必须改的旧锁"）。

**怎么证明**：田地离开磨坊就盖不下去（新 BuildBlock `no-mill-adjacent`）；面包 0 时盖民居必被挡且提示含"面包"；
磨坊邻 0/1/3 块田地 → 每回合面包 1/2/4。

**风险**：面包进 `cost` 之后，"资源不够"这一句要能报出**缺的是面包**，否则玩家不知道去哪补 → 改 `BLOCK_TEXT.cost` 为逐项列出。

## P-006 人口改成"岗位 + 快照"，缺员不挡建造只挡工作

**改什么**：`BuildingDef.population`（占用）→ `jobs`（需求，不闸门）；
新增回合快照 `approvedPopulation`；`staffing()` 按建造顺序（id 升序，与矿脉分配同口径）依次满足 jobs，
排不到的楼 `understaffed`；缺员的塔不开火、缺员的兵营不产兵；头顶 DOM 徽章"头像 + ✕"。

**会动到哪一面**：**这是本轮最大的一处"改答案"**。以下旧锁必须改口（不是我做砸了，是规则变了）：
- `tests/world.test.ts` 里"人口不足 → 盖不了"那几条：改成"人口不足照样盖得上，但楼缺员"。
- `BLOCK_TEXT.population` 与 `BuildBlock 'population'`：删除。
- `populationUsed()/populationFree()`：语义从"建造闸门"变"岗位需求 vs 快照容量"，函数留着，调用点变。
改口时**逐条在板子里登记改了哪条断言、原来断什么、现在断什么**，不许静默改。

**怎么证明**：同一局里"先盖 5 栋塔（jobs 5）但 approved 只有 3" → 恰好后建的 2 栋 understaffed（按 id 序）；
拆掉一栋民居 → **本回合内** staffing 不变（快照），结算后立刻有 2 栋翻成缺员 —— 这条正是他举的例子，必须有锁。

## P-010 材质自己调 + 独有 ID + 默认保存（用户 2026-10-20：「这个不错，可以让用户自己调，然后同时输出一个独有ID，改默认保存」）

### 1. 打算改什么

- 游戏内开一个**材质面板**：木纹明度 / 色阶档数 / 纹路密度 / 板宽 / 板缝深浅 / 像素块放大 / 种子变体 / 镀金强度，
  外加三档预设（淡·中·重）与一键回到默认。
- 每次改动**同时输出一个独有 ID**（形如 `mk-1q7x3fa`）：同一套参数永远同一个 ID，
  能复制、能贴回来还原（输入框 + 应用）。这是给玩家互相分享长相用的，不是随机串号。
- **默认保存**：没有"保存"按钮，滑杆一松就写进本地偏好（`Prefs`，无痕模式自动退回内存），下次启动直接读回来。

### 2. 根据的读数

- 现量：默认木纹生成 161ms、镀金 68ms（48×48 / 64×64，浏览器实测）。**所以拖动过程中绝不重算纹理**，
  会掉帧：明度/对比/像素块这三条走 CSS 变量即时预览，只有改变像素形状的那几条（档数/密度/板宽/板缝/种子/镀金）
  才在 220ms 防抖后重算一次。
- ID 位宽算过：八个字段量化后共 28 bit，base36 六位容量 2.17e9 > 2^28 = 2.68e8 ⇒ 放得下且不撞。

### 3. 会动到哪一面

- **只有界面与本地偏好**：玩法数值、经济、战斗、旗子一概不碰；199 条锁一条不该动。
- **只有时间**：改一次形状类参数多 ~160ms（面板上就把这个数显示出来，藏不住）。
- **崩了丢多少**：偏好只有一个键，坏了最坏是回到默认长相；ID 是纯函数派生，不额外存。

### 4. 怎么证明 / 每条怎么打红

| 锁 | 夹具 | 打红姿势 |
| --- | --- | --- |
| 往返不变 | 随机 500 组参数：`decode(encode(t)) == t` | 把某字段位宽写少一位 → 高位被截 → 红 |
| 确定性 | 同参数两次编码字符串全等 | 引入 `Date.now()`/随机 → 红 |
| 不撞号 | 2000 组随机参数 ID 去重后仍 2000 | 位宽不足会立刻撞 |
| 默认 ID 钉死 | 默认参数 → 一个写死的串 | 有人偷偷改默认值会红（这是故意的） |
| 非法 ID 不采纳 | `"mk-zzz"`、空串、超长串 → 返回 null 且当前配置不动 | 解码不校验就会静默变一套长相 |
| 存盘读回 | 内存桩 Prefs：存 → 新实例读回相等 | 键名写错就红 |

### 5. 风险与代价

1. 滑杆即时预览（CSS）与真正重算（像素）之间会有**一点点观感差**：拖动时看到的是滤镜后的旧纹理，
   松手 220ms 后换成真纹理。这是为了不掉帧故意做的取舍，面板上写明。
2. 参数字段一旦发布就进 ID 编码，**以后加字段必须升版本号**（ID 前缀那一位就是版本），
   否则老 ID 会被解成新含义。默认版本 = 1。
3. 面板本身要能用手指点准：滑杆用原生 `input[type=range]`（触摸友好），按钮最小 44px。

### 两处偏差 / 更正（如实记）

1. §2 我拿"木纹生成 161ms"当防抖依据 —— **那个数是冷启动**（含 canvas/PNG 编码 warm-up）。
