# 分发版准备 + 「HTML 快速开发版 → 自己的游戏引擎」探讨（2026-11-06）

用户："桌面分发版就定为 HTML，安卓端可以有一个测试分发版。另外咱们先探讨：
这个 HTML 快速开发版能不能迁移成自己的游戏引擎？"

> **本轮只做了分发版与探讨文档；引擎部分一行游戏代码都没动**（用户说"先探讨"）。

---

## 一、结论先说

| | 桌面分发版 | 安卓测试分发版 | 自研引擎 |
| --- | --- | --- | --- |
| 形态 | **纯 HTML 静态站点**（`dist/` + zip） | **debug APK**（Capacitor 7 把同一份 dist 装进 WebView） | **只探讨，不动代码** |
| 交付物 | `releases/GAMEKAR-desktop-html.zip`（1.1 MB） | `releases/GAMEKAR-arena-debug.apk`（5.3 MB） | 本文第四节 |
| 入口 | `/` 老模式、`/arena.html` 对战 | 一开就是**对战模式**（老模式留 `classic.html`） | — |
| 安装 | 任意静态托管 / 本地 HTTP server | `adb install`，需允许未知来源 | — |
| 能不能上架 | TapTap H5 路线（另需登录/备案，见下） | **不能**，debug 签名、只作内部测试 | — |

**自研引擎一句话结论**：能，但不是"把 HTML 换成引擎"，而是"把现有分层**提炼**成引擎"。
最值钱的那块（`ArenaWorld` 纯逻辑、20Hz 固定步长、seed 可复现）已经是引擎内核了；
目前最不建议做的是自研 WebGL 渲染器去替 Three.js —— 收益最低、风险最高。

## 二、分发构建链（已实跑通）

```
npm run dist:web      # tsc + vite build → dist/（桌面 HTML 分发物）
npm run android:web   # dist:web + 生成 dist-android/（对战模式做 index.html、去掉 sourcemap）
npm run android:sync  # android:web + 同步 WebView 资源（tools/sync_android_web.mjs）
npm run android:apk   # android:sync + Gradle assembleDebug + 复制 APK 到 releases/
```

工程文件：`capacitor.config.ts`（appId `com.gamekar.arena`）、`android/`（Capacitor 原生壳，
已改包名/应用名）、`tools/android-init.gradle`（国内 Maven 镜像）、
`tools/prepare_android_web.mjs` / `sync_android_web.mjs` / `build_android_apk.mjs`。

**APK 实测**（`aapt dump badging`）：

```
package: name='com.gamekar.arena' versionCode='1' versionName='1.0'
sdkVersion:'23'  targetSdkVersion:'35'  application-label:'GAMEKAR'
uses-permission: android.permission.INTERNET
```

包内 `assets/public/index.html`（对战）/`classic.html`（老模式）/`assets/dudes/*` 齐全，
sourcemap 为 0 个。**游戏运行时不需要网络**——素材与代码全在包里；INTERNET 权限来自
Capacitor 模板，正式版可删（要同步删掉 Cordova 插件桥的引用）。

### 本机环境实测（照着复现才不会踩坑）

| 项 | 本机值 / 坑 |
| --- | --- |
| Node / npm | 22.22.2 / 10.9.7 |
| JDK | 默认 `java` 是 1.8、`JAVA_HOME` 还指向**不存在的** Adoptium 目录 → 脚本验证 `bin/java.exe` 后回落 Android Studio JBR（OpenJDK 21） |
| Android SDK | `C:\Users\li\AppData\Local\Android\Sdk`（platforms 27–36、build-tools 35/36） |
| Gradle | wrapper 的 8.11.1-all.zip 走 Java HTTPS 会 SSL 读超时 → 用 curl 从腾讯云镜像拉 bin 包解压到 `~/.gradle/gradle-local`，脚本自动优先用它 |
| Maven | `dl.google.com` / `repo.maven.apache.org` 在 Java 里读超时 → `tools/android-init.gradle` 把阿里云/腾讯云镜像**插到仓库最前**（不删官方源） |
| safe-delete 代理 | 本机 WorkBuddy 会拦 `fs.rmSync` / `cap sync` 的插件缓存删除 → 准备/同步脚本走 cmd 内置 `rmdir/del`，`android:sync` 用项目内脚本代替 `cap sync` |

> 这些是**本机环境 workaround**，不是游戏设计。`android-init.gradle` 与两个脚本对正常
> 机器也成立（镜像只是备用源）；`cap sync android` 在无代理的机器上仍是标准做法。

### 分发红线（还没做，别拿去上架）

1. APK 是 **debug 签名**，只给内部测试；正式包要 release 签名 + versionCode/Name + 混淆规则；
2. **没接 TapTap 登录、没做小游戏前置备案**（沿用 `上架与联机评估_20261105.md` 的结论：
   走 H5 游戏路线，不是 Tap 小游戏 WebGL）；
3. 商店素材还缺 9:16 竖版实机截图；防沉迷口径按平台形态确认；
4. 联机若上，**必须和备案同一版做完**（官方 FAQ：单机改联网要重做资质）；
5. 桌面 HTML 用 `file://` 直接开会有模块/CORS 限制，必须走 HTTP 静态托管。

## 三、为什么安卓用「HTML 装进 WebView」而不是重写

- **一份产物两条分发**：`dist/` 既是桌面版也是 APK 的内容，不存在"两套逻辑不同步"；
- 之前实测：`ArenaWorld` 不 import three、固定 20Hz、seed 可复现，逻辑层本来就与浏览器无关，
  只有渲染/HUD/音频/存档贴在 Web 平台上 —— WebView 恰好把这些平台能力原样提供；
- PWA（安装到主屏）是第三条零成本通道，需要时加 manifest + service worker 即可，
  本轮没做，避免把"测试分发"复杂化。

## 四、自研引擎探讨（不动代码）

### 4.1 先把"引擎"这个词拆开

同一个词至少指三件完全不同的事，代价差着两个数量级：

| 含义 | 要做什么 | 我们的现状 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 内部 SDK／分层引擎** | 把 `engine/` 提成独立包 `@gamekar/engine`，定死依赖方向、写 API 文档与示例 | `engine/` 已有 10 个文件（GameLoop / CameraRig / Renderer / Viewport / Grid / Noise / Random / PointerInput / EventBus / Lighting），README 已有"engine 不许 import game、game 不许 import ui"的规矩 | **低**。主要是整理与锁（依赖方向用测试钉住） |
| **B. 平台抽象引擎** | 定义 Renderer / Input / Audio / Storage / Timing 五个接口，浏览器是一种实现；将来可接原生/无头服务器 | 目前 Web API 分散在视图层：`src/arena` 里 6 个文件直接用 `document/window`，`Web Audio` 在 `src/audio/sfx.ts`，`localStorage` 在 banner/sfx | **中**。要拆 DOM HUD 这一层，但不动游戏规则 |
| **C. 自研渲染器／运行时** | 自己写 WebGL/WebGPU 或原生渲染，替换 Three.js 与 DOM | Three.js 出现在 **24 个视图层文件**；DOM HUD 是完整 UI 系统 | **高**。数月级、收益最低，还会拖住内容迭代 |

**判断标准**：引擎的价值 = 可复用 × 边界清晰 × 与具体游戏解耦，不是"有没有自己写的渲染管线"。

### 4.2 现状盘点（实测，不是印象）

| 层 | 文件数 | 依赖 | 评价 |
| --- | --- | --- | --- |
| `engine/` | 10 | 只依赖 three 的 3 个渲染件 | 已是通用能力层，但与 `game/world/*` 有交叉 |
| `arena/`（对战） | 29 | `ArenaWorld` **不 import three**；视图层依赖 three/DOM | **最值钱的资产**：逻辑可直接在 node/服务器跑（471 条测试就是证据） |
| `game/`（老模式+素材） | 34 | three / DOM 混合 | 抽卡、兵种表纯数据；视图与逻辑混着 |
| `ui/` | 21 | DOM/CSS | 浏览器绑定最重 |
| `audio/` | 1 | Web Audio | 音效全合成，零素材，接口很干净 |
| `styles/` | 5 | CSS | HUD/菜单全是 DOM |

**资产**：
- `ArenaWorld` 纯逻辑 + 固定 20Hz + seeded RNG ⇒ 服务器/回放/测试三用（联机评估已确认）；
- 471 条锁把规则钉住，重构有安全网；
- 规则与文案同表、`onState` 只做镜像，DOM HUD 不自己算判据 —— 这是分层做对的地方。

**负债**：
- `CameraRig` 是**正交投影**且 `worldPerPixel/screenToGround` 与它绑死（换透视相机要重做一轮，之前记录过）；
- HUD/菜单用 DOM，B 阶段必须决定"UI 也抽象"还是"UI 永远 Web"；
- `GameApp`（老模式）与 `ArenaApp` 各自装配，缺少统一的 App/Scene 生命周期接口；
- `Math.random` 只在视觉层（扬尘/音高）残留，逻辑层 0 处 —— 保留即可，别顺手改成全局禁用。

### 4.3 建议路线（按依赖顺序，可随时停）

1. **阶段 A：边界固化（低成本、立刻有收益）**
   - 把 `engine/` 做成 workspace 内独立包，依赖方向写成测试锁（"engine 不 import game/ui"现在是文档，不是锁）；
   - 给 `ArenaWorld` 补一份"headless 用法"文档/示例：node 里跑一局、无 WebGL；
   - 这一步做完，就可以说"我们有一个游戏内核"了。
2. **阶段 B：平台接口（中等，按需触发）**
   - 定义五个接口：Renderer / Input / Audio / Storage / Timing；浏览器实现保持现状；
   - HUD 先留在 Web 实现里（承认"UI 是平台相关"），别为了纯净化把 21 个 UI 文件全重写；
   - 触发条件：**要出第二个前端**（原生 App 自定义 UI / 服务器回放器 / 编辑器工具）时才做。
3. **阶段 C：换渲染后端（不推荐现在做）**
   - 只有出现明确的硬需求（包体/性能/特定平台不支持 WebGL）才评估；
   - Three.js 压缩后约 124KB gzip，dist 去 map 后 1.1MB，它不是当前瓶颈。

### 4.4 与联机/上架的关系（最容易顺手做错的地方）

- 联机建议的**状态同步**方案本来就要求服务器跑一份 `ArenaWorld` —— 阶段 A 的 headless
  内核正是这个前提，所以"引擎化"和"联机"不冲突，反而是同一条路；
- 但联机必须与备案同一版完成（资质红线），**不要为了引擎重构顺手改规则**；
- 安卓 WebView 壳 + 桌面 HTML 已经证明"多前端"可行，暂时不需要自研运行时。

### 4.5 明确不建议

- 自研 WebGL/WebGPU 渲染器替 Three.js；
- 为了"引擎"把 DOM HUD 改成自绘 UI；
- 在只有一个游戏、且规则还在每周迭代时做大规模抽象（过早抽象的返工率最高）。
