# AI 决策架构 & 音效分层（2026-11-06）

用户原话：

> 「AI 机器人也要强化，整个架构你帮忙处理一下，文档要有注释且清晰。
>  因为我们加了小房屋的各种新约束，AI 机器人也要学会刷新卡片。
>  我这边音效有点混乱，我怎么感觉对方获得一个金币的音效，我也能听到。」

这份文档把**架构**、**判据**、**实测读数**和**还没解决的问题**分开写。
代码里的注释与这里是同一套口径：`src/arena/ai.ts` 顶部有三层架构图，
`ArenaApp.audioCues()` / `syncBuildings()` 里标了音效分层。

## 一、AI：三层架构

```
① 局面读取   AiView                      src/arena/ai.ts
   世界把「能看的」打包过来，大脑不读全局状态
      ├─ hand     四张手牌（null = 补牌中）
      ├─ gold     当前金币
      ├─ count    场上各类楼的数量
      ├─ supply   ★ 人口/面包容器（复用 ArenaWorld.supplyOf()）
      └─ rerollIn ★ 距下次可刷新还有几秒
                    │
                    ▼
② 决策（纯函数，唯一入口 decide()）
      ├─ constrainedWish(view)  按容器重排愿望清单
      ├─ shouldReroll(view)     该不该花 5 金换牌
      └─ chooseCard(view)       出第几格 / 攒钱
          输出 { kind: 'reroll' } | { kind: 'play', slot } | { kind: 'wait' }
                    │
                    ▼
③ 执行   ArenaWorld.think()               src/arena/ArenaWorld.ts
     只按 action 动手：reroll() / play() / 什么都不做
     ★ 这一层不做任何判断 —— 改策略不用碰世界状态
```

**为什么这么拆**：2026-10-28 那次「AI 一直出弓箭手」的 bug 埋在 `ArenaWorld`
一千行里，要跑完整局才测得出来。现在给一份 `AiView` 就能单测
（`tests/ai.test.ts`，10 条纯函数锁）。

### `AiView` 两个新字段是可选的

`supply` / `rerollIn` 不传时全部退回旧行为 —— 旧调用点和旧单测
（`tests/arena.test.ts` 里直接调 `chooseCard` 的那几条）不用跟着改。

## 二、新约束下 AI 学会的三件事

### ① 不再挑「打不出去的牌」

`canPlay(card, supply)` 先剔掉容器不允许的牌：

| 卡 | 判据 |
| --- | --- |
| 民居 | **永远能落**（它自己 +2 上限且不占人口）—— 这条很关键，否则 6/6 满时连民居都盖不出来 |
| 其它建筑 | `pop + 2 <= popMax` |
| 军队（n 人） | `pop + n <= popMax` **且** `bread + n <= breadMax` |

**反证锁**：不传 `supply` 时 `canPlay` 必须放行所有牌（旧行为），
传了满容器时必须拦下塔和军队 —— 两边都测，不是自证。

### ② 卡住了会花 5 金刷新

`shouldReroll(view)` 的**三道闸**：

1. `rerollIn > 0` → 不刷（冷却 12 秒）
2. `gold < REROLL.cost + AI.minReserve`（5 + 10 = **15 金**）→ 不刷（刷完还得留够出一张牌）
3. 手牌为空 → 不刷（空手会自然补，不用花钱）

过了闸，只有两种「卡住」会刷：

- **a. 一座民居都没有 + 手里没有民居 + 手里也没有任何建筑卡**
  → 刷。`reroll()` 保底给一张民居，正好补上「建筑协调经济」的起点。
  加「手上没有建筑卡」这一条是实测逼出来的：开局一缺民居就刷，会让 AI
  把钱全交给刷新，**实测红方 120 秒一个兵没出**。
- **b. 手牌里一张能落得下去的前 3 想要都没有**（全被人口/面包挡住）→ 刷。

刷新成功后 `think()` 给 `aiRerollIn[side] = AI.rerollCooldown`。
**玩家手动刷新不占这个计时器**（玩家不是 AI）。

### ③ 攒钱有上限

`chooseCard` 里「建筑值得等」保留，但加了兜底：
`gold >= 16` 且手上有出得起的军队时，先出军队推线 —— 金币上限 20，
攒到 16 还不花就是纯浪费。

## 三、音效分层（第二个问题）

**先说实测，不猜**：浏览器里钩住 `sfx.play()` 跑 16 秒，
得到 `{"coin": 2, "build": 1}`，金币变化记录：

```
t=22 dB=1 dR=1     t=24 dB=1 dR=1     ← 两边同时跳格
t=26 dB=0 dR=1  …  t=36 dB=0 dR=1    ← 蓝方已封顶 20，只剩红方涨
blueEnd=20  redEnd=6
```

`coin` 本来就只读 `world.gold.blue`，没有串台。**真正串台的是 `build`**：
建筑完工那串「木材堆放」敲击声之前是**全场播**，红方立好一栋楼也响，
听起来就像「对面拿了一笔钱」。

### 分层规则（代码注释与下表一致）

| 类别 | 音效 | 谁听得见 | 理由 |
| --- | --- | --- | --- |
| 我方建造 | `build`（完工）、`place`（出牌）、完工震屏 | **只蓝方** | 对方的资源变化不该给我反馈 |
| 全场战斗 | 开火 / 命中 / 近战 / 阵亡 / 整栋倒塌 / 倒塌震屏 | 双方 | 它们发生在玩家视野里，静音反而让战场变哑 |
| 结算 | `win` / `lose` | 全局一次 | — |

> 2026-11-06 更新：`coin`（金币到账）已按用户要求**整条撤掉**（"金币获取的声音太吵了，
> 把它关掉吧"）——2 秒一格 + 磨坊产金，声音比动作密得多。撤的是触发点
>（`audioCues`）和合成器两处，分层原则不变。

`audioCues()` 另加一道保险：用 `Math.floor(gold)` 的**整数格跨越**判涨，
浮点抖动不会骗出一声 coin。（该判据随 coin 一并撤除。）

### 修复后的反证实测

```
红方楼完工 → build 播放 0 次
蓝方楼完工 → build 播放 1 次
同时段 coin 播放 1 次（我方金币跳格）
```

## 四、退化读数 → 定位 → 修好（2026-11-06 第二轮）

### 先认两次错判

上一版在这里写「瓶颈是 `wishList()` 无限追求民居，下一轮该动建筑目标上限」。
**这个判断被单局探针证伪了**：

```
seed 20261027 红方 180 秒：plays 11 / waits 59 / rerolls 11 / peakUnits 3
topWanted: "house|mill|barracks" 49 次、"mill|house|barracks" 19 次
建筑: 塔 3、民居 4、兵营 1、磨坊 0     supply: 面包 3/3 满
```

第二轮又试了两处，都按「只改一处、单独量 24 局」的办法验证，**都是负收益或无收益，已撤回**：

| 尝试 | 24 局拆楼 | 结论 |
| --- | --- | --- |
| 掐掉「容量满就刷新」 | 1.4 → **1.1**（平局 10→14） | 刷新虽然烧钱，但让手牌流动；掐掉更僵，撤回 |
| 刷新保底改成「缺什么给什么」 | 1.4 → **1.4**（读数一模一样） | 没走到那条路径：`missingLogistics()` 几乎总返回 house |

还有一句也要改口：上一版说「双方 120 秒一个兵没出」——那是**结局快照**，
`units=0` 是兵死光了。24 局平均兵峰值其实有 **8.8**。拿结局当峰值，是读数口径错误。

### 只读实验：面包到底是不是瓶颈

临时改 `SUPPLY.baseBread` 跑 24 局（跑完还原，**产品数值没动**）：

```
baseBread=3 → 拆楼/局 1.38 | 兵峰值 8.8
baseBread=4 → 拆楼/局 1.83 | 兵峰值 9.5   (+33%)
baseBread=5 → 1.83 / 9.4    （饱和）
baseBread=6 → 1.83 / 9.5    （饱和）
```

面包是**边际约束**，不是主瓶颈；而且 +1 之后就饱和。
但 3 是用户实测定的数值，改它会破坏「面包是副闸」的设计 —— **不改数值**。

### 真正的病灶：`missingLogisticsAll()` 的二选一

`mill` 卡在 seed 20261027 全程只在手牌里待过 **89 帧**（house 742 帧）。原因：

- 旧判据 `mills < barracks`：**没盖兵营时 `barracks=0`，永远不认为缺磨坊**，后勤保底从不发 mill；
- 磨坊是**唯一**能扩面包上限的建筑（基础 3 + 每座 2）；
- 一队 3 人弓箭手一次吃光 3 点面包 ⇒ 之后所有军队卡被 `canPlay` 拦死 ⇒
  `shouldReroll` 条件 b 触发刷新 ⇒ 保底 house 把刚补到的 mill 换掉 ⇒ 循环。

修法（**判据层，不动数值**）：`mills < Math.max(1, barracks)` —— 至少要有一座磨坊；
同时 `draw()` 的后勤保底改成遍历所有缺口（手上已有第一张就补第二张），
`reroll()` 保所有缺口并且**永远仍保一张房屋**（用户原话「刷新默认给一张房屋」不破）。

### 结果

| | 修之前 | **修之后** |
| --- | --- | --- |
| 24 局拆楼/局 | 1.4 | **1.8**（+29%） |
| 蓝 胜/负/平 | 10/4/10 | **9/6/9** |
| 结束率 | 24/24 | 24/24 |
| `mill` 在手帧数 | 89 | **809**（判据真的被调用、有产出） |
| 单局 plays / waits / 兵峰值 | 11 / 59 / 3 | **15 / 52 / 5** |
| 红方磨坊 | 0 | **1** |

1.8 正好撞上只读实验 `baseBread=4/5/6` 的饱和值 1.83 —— **因果闭环**：
让磨坊早点进牌池 ≈ 扩了面包上限，但没动数值。

### 锁（420 全绿）

新增反证：`开局什么都没盖时刷新必带 mill + house`（旧判据必错）、
`已有一座完工磨坊就不再算缺口`（防每次刷新都硬塞磨坊）、
`缺磨坊时刷新保 mill + house`、`什么都不缺仍保房屋`。

### 还没解决的（留下一轮）

拆楼 1.8 仍低于加施工前的 2.6，平局 9 局。**别再调 AI 了** —— 兵峰值 8.8~9.5 说明兵出得来，
问题是**推不动**。下一轮该量的是「兵最远推进到哪一列 / 交火发生在哪一侧」，
而不是继续在发牌策略上打转；判据依旧只看拆掉对方多少，不看盖了多少栋。

> 追记（同日晚 P-039）：「兵推不动」的根因在规则层 —— 兵营的兵占人口，
> 楼把基础 6 人口占光后产线没起步就封顶。改成「兵营的兵不占人口」后
> 24 局拆楼 1.8 → 2.7，AI 一行没改。同日的价格调整（P-041）后 → 4.1。

## 五、槽位制衡 + AI 评估（2026-11-06 第三轮，P-042，设计先于实现）

用户原话：

> 「AI 可能会更聪明一点，会克制的建筑优先建造民居，然后会自己评估适合建什么、
>  不应该建什么，或者当前不能建什么。……不能一建一堆建筑物，最高是需要留一些
>  槽位来给我们的军队的，有一个制衡。」

### ① 槽位制衡（规则层，AI 只是被它约束的一方）

新规则：**建筑占用的人口最多到 `人口上限 − SUPPLY.armyReserve`（=2）**。

- 为什么是规则而不是 AI 习惯：玩家同样受这条管 ——「留军队槽位」是双方对称的
  容器约束，跟人口/面包同一条法律。AI 的"聪明"只是**比玩家先读懂它**；
- 民居例外照旧：先加容器再看占用，所以名额顶住时**民居永远盖得出来**（不死锁）；
- 军队卡不受这条限制（保留槽就是留给它的）；
- 被顶住时 `supplyBlocked` 的理由带「人口」二字 ⇒ HUD 胶囊闪红同一条路。

### ② AI 评估：每张牌分三类

`assess(card, view)` 纯函数，返回 `'ok' | 'unwise' | 'blocked'`：

| 类别 | 判据 | AI 怎么做 |
| --- | --- | --- |
| **blocked（当前不能建）** | `canPlay` 不过（容量/保留槽顶住） | 不选；全 blocked 时走刷新 |
| **unwise（不应该建）** | 见下表 | 有 ok 先出 ok；全 unwise 时刷新 |
| **ok（适合建）** | 其余 | 正常按愿望清单出 |

「不应该建」的判据（都算得出来，不靠手感）：

| 卡 | 不该再建的情形 | 理由 |
| --- | --- | --- |
| 民居 | 已有 ≥ 消费者数 + 1（塔+兵营+1） | 名额够用还盖是白花钱 |
| 磨坊 | 已有 ≥ max(1, 兵营数) + 1 | 面包上限够用 |
| 兵营 | 手上没有能接住的空余后勤（磨坊 < 兵营+1 或民居名额不够） | 盖出来也是死楼 |
| 塔 | 民居名额不够再养一座 | 盖出来不开火 |
| 军队 | 永远 ok（军队是保留槽的主人） | — |

克制优先民居：`constrainedWish` 在**建筑名额被保留槽顶住**时把 house 顶到最前
（民居是唯一解锁，不存在旧注释担心的"差 1 格循环"——那是结构性的顶死，不是边际差 1）。

### ③ 验收口径（先写下来，实现后照着量）

- 逻辑锁：保留槽拒建筑（理由带「军队」）、民居不死锁、军队不受限、
  AI 三类评估各一条、`constrainedWish` 顶 house 一条；
- 24 局读数对比 P-041（拆楼 4.1 / 蓝 6-14-4）：拆楼不应明显倒退；
  蓝方劣势问题独立记录，本轮不背这口锅也不顺手修。
