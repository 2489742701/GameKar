# P-005 建筑模型整体重做（2026-10-27）

用户原话：「你可以写个计划吧，然后把他们的一些模型都重做一下。我看模型重做之后，越重做越丑啊」，
并点名**箭塔**要重做好看一点。

## 0. 先说为什么"越重做越丑"

不是审美问题，是**工作方式**的问题：这一路我都是"改一版 → 让你看 → 你说丑 → 再改一版"，
而我自己**看不见**模型（应用内浏览器长期 `visibilityState=hidden`，截图拿不到）。
于是每一轮都在盲改：加一块、削一块、换个色，越叠越碎。**先修工作方式，再修模型。**

## 1. 打算改什么

- **建一个离线的等轴预览器**（`tools/preview_models.mjs`，只在开发期用）：
  把 `ModelSpec` 里的原语（box / prism / plinth / cyl / cone / sphere / crystal）
  按游戏里同一套机位（yaw 0°、pitch 50°）投到平面上，画成 PNG 排版图。
  亮度用"面法线 · 光向"算，只为判断**剪影、比例、配色**，不做真渲染。
  ⇒ 从此每一版模型我都能**先看再给你看**，不再盲改。
- **重做一套对战模式的建筑**，五件一起定，不再一件一件打补丁：
  议事厅（核心）/ 兵营 / **箭塔** / 炮塔 / 磨坊。
  全部自建（不再借用老头模式的模型库），共用一套设计语言（见 §2）。
- 旧的 `game/models/*` 一行不动 —— 老头模式（`/`）照旧。

## 2. 设计语言（这轮先定死，避免又漂）

| 项 | 规矩 | 理由 |
| --- | --- | --- |
| 占地 | 3×3 格，模型视觉占 **2.5–2.8 格** | 占满了会互相顶到，留一点缝才看得出"一栋一栋" |
| 高度 | 兵营 1.4 / 磨坊 2.0 / 箭塔 2.6 / 炮塔 1.8 / 核心 2.2（模型单位，最后统一 ×2.2） | 远看要有高低差：塔最高、兵营最矮 |
| 剪影 | 每栋必须有**一个唯一识别符**：核心=尖顶+水晶、兵营=双坡脊+门、箭塔=四角垛口+箭窗、炮塔=圆台+炮管、磨坊=风扇 | 俯视角下细节会糊，只有剪影可靠 |
| 配色 | 墙体 `#c9b795`、木 `#6b4526`、石 `#6a6f7c`、屋瓦 `#a8483c`；**阵营色只出现在小面积**（旗、炮塔四角、核心水晶） | 大面积阵营色会被当成地形 |
| 细节密度 | 每栋 ≤ 14 个原语 | 多了就是"碎"，这条是这轮把丑治住的关键 |
| 不许 | 悬空件（除了水晶/旗）、互相穿插、贴地的纯色板 | 这三样是前面几轮被否掉的原型 |

## 3. 会动到哪一面

- 只动 `src/arena/`（模型 + 视图接线）。老模式、引擎、素材包不动。
- 数值（血量/价格/射程）**一个都不动**：这是纯外观重做。

## 4. 怎么证明"改了但没改坏"

- 现有 **295 条锁**必须全绿（模型重做不该碰任何判据）。
- 预览器自己也要能被验证：同一份 `ModelSpec` 两次出图字节相同；
  换机位（pitch 变）图会变 —— 两条自证，防止"预览器其实画错了但我当成模型丑"。
- 外观好不好看**不由我断言**：我把预览图给你看，你点头才算。

## 5. 风险与代价

1. 预览器是"假渲染"（平行光 + 平面着色，没有阴影/环境光），所以**它好看 ≠ 游戏里好看**；
   我会用同一机位、同一比例出图，尽量缩小差距，但最终仍以你的实机为准。
2. 五件一起改，中间的版本会短暂不一致（比如核心换了新语言、兵营还是旧的）；
   所以这轮**一次性提交**，不留半成品。
3. 预览器只进 `tools/`，不进产品包。

## 7. 回填（2026-10-27 03:10，落地结果）

**先更正第 0 节的一句**：截图不是拿不到 —— 用 browser-use MCP 的页面截图直接拍到了真画面。
之前"看不见"只针对页内 canvas 截取那条路。所以这轮的实际工序是
**预览器粗调（秒级）→ 真页面截图定案**，比原来计划的"只靠预览器"更稳。

### 7.1 实测尺寸（格，已 ×BUILDING_SCALE=2.2）

| 建筑 | 宽×深 | 高 | 原语数 | 识别符 |
| --- | --- | --- | --- | --- |
| 核心 | 4.0×4.3 | 6.4 | 14 | 两段石座 + 四坡顶 + 屋顶水晶 |
| 兵营 | 3.6×2.7 | 3.0 | 12 | 横长双坡脊 + 门 + 矛架 |
| 箭塔 | 3.0×2.8 | 6.2 | 14 | 外挑垛口四齿 + 锥顶 + 金顶珠 |
| 炮塔 | 3.6×3.1 | 2.9 | 13 | 木台 + 四角阵营色防撞块 + 横炮管 |
| 磨坊 | 3.7×2.9 | 5.7 | 13 | 木栈道 + 阵营色尖顶 + 四片白帆 |

对照：**旧核心实测 7.96 格宽 / 6.09 格高**，屋顶比 3 格占地宽一倍 —— 这就是"越重做越丑"的根。

### 7.2 落地时改掉的四处旧毛病

1. **旧模型是手写 three 的三份私有实现**（makeCore/makeMill/makeCannon）+ 模型库两份，
   同一栋楼两套坐标口径。现在五栋全部走 `models.ts` 数据 + 套件 `buildModel`。
2. **旗子挂在背对镜头的墙上**（旧 `bannerSpot` 的 z 为负），而且高度低于屋顶 ⇒ 布埋进屋顶、
   只在瓦面上投出一块黑影。新 `ARENA_FLAGS` 按模型给落点，全部在可见侧。
3. **血条高度、裂纹位置、掉渣范围按建筑种类写死**（`barHeightOf` 等）。改成建好后量一次 bbox。
4. **帆/炮塔各写一套转轴**。改成套件现成的 `spin`/`turret` 字段，视图只读 `userData`。

### 7.3 验证

- `npx tsc --noEmit` 干净；**22 个测试文件 / 300 条全绿**（新增 `tests/models.test.ts` 5 条）。
- 变异检查：把核心屋顶半径从 1.22 改回 2.6 ⇒ 体型锁立刻红；还原即绿。
- 真页面：五栋楼同时在场的截图确认 —— 帆在转（rotation.z 随时间走）、炮塔朝目标（aim=0.24 → 转 -0.24）、
  兵营 6 秒出兵、控制台零报错。
- **外观仍待他点头**：我只能证明"比例对不对、旗在不在、转不转"，好不好看由他拍。
