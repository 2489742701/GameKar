# PVE 模式设计（2026-11-07）

用户："按照代办把 PVE 模式做一下。PVE 模式可以单人打，也可以多人打，场地贼拉大。"

> 待办清单在 `PVE模式待办_20261106.md`；本文是**设计定稿**，把待办里没定口径的
> 六件事拍下来，并说明为什么这么拍。实现跟着本文走，改口径先改本文。

---

## 0. 一句话

**横版守家**：玩家在下方（col 小），怪从上方（col 大）按波次涌下来，
撑过全部波次（或守满 5 分钟）就赢、大本营被拆就输。场地比 1v1 大 2.2 倍（1920 格），
双人同屏时两人共守这条线。

---

## 1. 场地（"贼拉大"的落点）

| | 1v1（不变） | PVE |
| --- | --- | --- |
| cols（屏幕上的纵深 / 高度） | 44 | **60** |
| rows（屏幕上的宽度） | 20 | **32** |
| 面积 | 880 格 | **1920 格（2.2×）** |
| 玩家可建区 | 蓝 col 0~21 | **blue col 0~29** |
| 禁建带 | 9 列（midCol 22±4） | **9 列（midCol 34±4，col 30~38）** |
| 敌对出生区 | 红 col 23~43 | **走廊 col 39~59，出生点 col 46** |
| 长宽比 | 1 : 2.2（横） | **1 : 1.9**（贴手机竖屏） |

- **先加宽、才加长**（20 → 32 行）：一行只有 6 栋 3×3 的宽度，双人 / 多路根本铺不开；
  32 行 = 10 栋并排，才有"大场地"的读图感。纵深 44 → 60 是配套，让怪有行军距离。
- **纠错记录（重要）**：一开始拍的是 **56×36**（更方），实机竖屏截图里战场被压成横向一条，
  上方和下方各留一大片黑。原因是 `col` 轴被机位映射成**屏幕水平方向**，
  竖屏要的是"纵深大、宽度中等"。改成 **60×32** 并配合 yaw 270 才贴满屏幕。
  **形状比面积更重要**，别只看"2.3 倍"这个数字。
- `FIELD` 常量仍是 1v1 的口径（**1v1 一行不改**）。世界改成读实例字段
  `world.field`，PVE 传自己的尺寸；`TileMap`/`GroundView`/`stand`/`confetti`
  早就按 `world.fieldSize` 建，所以地面会自动跟着变大。
- 相机 `tilesAcross` 上限从 44 提到 60（大场地要缩得出去）。PVE 开局
  `fitZoom = rows × 1.02`（**按行数贴满，不是按列**），机位 yaw 270 / pitch 36，
  并把 `director.portrait` 关掉 —— 让"屏幕下方 = 自己家、屏幕上方 = 怪来的方向"。

## 2. 阵营：**不新增第三方 side**（关键取舍）

待办里写的是"波次怪需要 neutral/pve 第三方阵营"。**改成：怪就是 `red`。**

理由：`Side` 现在被 `Record<Side, …>` 铺满（金币、手牌、冷却、托管、AI 计时、
被拆数、summary…），加第三个阵营要改 30 多处，而且 1v1 里它永远用不到 ——
等于用类型系统换零收益。

PVE 里 `red` 只是**换了驱动方式**：

- 1v1：`tickAi('red')` —— 红方有金币、有手牌、有 AI 决策；
- PVE：`tickWaves(dt)` —— 红方没有金币手牌，按波次表直接生成单位。

`red` 的建筑在 PVE 里一座都不生成（含大本营），所以"打红方的楼"自然不成立，
判据也不看红方。

**多人**同理不加 side：多出来的是**玩家槽**，不是阵营 —— 见 §3。

## 3. 多人：同一阵营的多个玩家槽

用户要的"多人打"是**合作守家**，不是各自为战。所以：

- `PlayerSlot = { id, side, gold, goldTick, hand, cooldowns, lastPlayed, auto, aiIn, aiRerollIn }`
- 1v1：`[blue 玩家0, red AI]` —— 两人对打（现状不变）
- PVE 单人：`[blue 玩家0]`
- PVE 双人：`[blue 玩家0, blue 玩家1]` —— **两人都在下方，共守一条线**

出牌链全部改成**按玩家**操作：`playCardOf / canPlaceAtOf / rerollOf / placementProblem`
收 `PlayerSlot`，老的 `playCard(side, …)` 签名保留，内部转发 `playerOf(side)` ——
1v1 一个调用点都不用改。

> ⚠️ **踩过的坑**：`update()` 原来是 `for (const side of ['blue','red'])` 给两边涨金。
> 玩家槽化之后 PVE 里没有 red 槽，`playerOf('red')` 回落 `players[0]`，
> 等于**给蓝方刷了双份金币**。改成遍历 `this.players` 后"影子收入"消失，
> 12 局胜率从 9/12 掉到 3/12 —— 难度变化不是波次变难了，是之前的读数一直是虚的。

两个玩家各自一套金币 / 手牌 / 刷新冷却，**共用**一套人口 / 面包 / 民居（防线是一体的）。

为什么不做联机：联机要服务器跑同一份 `ArenaWorld` 广播快照，是独立立项
（见 `分发与引擎路线_20261106.md`）。同屏双人先跑通，`players` 数组就是将来
"多一个远端玩家"的接口 —— 不用再动规则层。

### 3.1 双人同屏的界面（2026-11-07 实现）

```
┌──────────────────────────┐
│  玩家1 的手牌（倒转180°） │  ← 手机平放桌上，对面那位看是正的
│  金币条 + 刷新           │
├──────────────────────────┤
│  共享顶栏：人口/面包/民居/波次 │
├──────────────────────────┤
│                          │
│        战 场             │
│                          │
├──────────────────────────┤
│  视角 · 正对    设置      │
│  玩家0 的手牌             │
│  金币条 + 刷新           │
└──────────────────────────┘
```

- **翻转而不是分屏**：`transform: rotate(180deg)` 只改视觉，DOM 顺序、事件、
  命中区域全不变 —— 两个人各看自己那一侧，不用挤到同一边歪头看倒字。
- 手牌压到 `opacity: .88`，让怪的出生区透出来一点（实测不压的话木纹底把上半场盖死）。
- **拖放按 `pointerId` 分槽**：原来只有一个 `dragFrom`，两根手指同时按会互相覆盖，
  表现是"我拖着拖着影子跑到他那边去了"。现在两个人可以同时各拖各的。
- 相机 `fitZoom` 双人再退 10%（`seatCrowd`）：上下各压一套手牌，
  不然自家最下面那排楼正好被手牌盖住 —— 大本营就在那儿。

### 3.2 三个人踩过的坑（同一个病根：`playerOf(side)` ≠ "这个 side 的所有玩家"）

| 位置 | 原来 | 后果 |
| --- | --- | --- |
| `update()` 涨金 | `for (const side of ['blue','red'])` | PVE 里 `playerOf('red')` 回落 players[0]，**蓝方刷了双份金币** |
| `tickAi()` | 同上 | **玩家 1 根本没被驱动**，一栋楼不出 |
| `options.auto.blue` | 只写 `playerOf('blue')` | **玩家 1 从开局就不是托管**，满手牌满金币站着看 |

②③ 叠起来 = "双人比单人还难"（5/12 vs 8/12），探针读数还看不出异常。
修完之后双人 12/12。**以后凡是"按阵营"的循环，先问一句：这个 side 可能有几个玩家？**

## 4. 怪的行为（单线推进）

待办 §4-1 问"右边一条线还是 PVZ 式多路"。**拍：一条推进方向、多个出生行。**

- 推进方向固定：沿 -col 走，目标永远是 blue 大本营；
- 出生行在关卡 `lane: [4, 26]` 之间按波次表分散（多路感来自出生点，不是分道地图）；
- **不追远处的兵**：索敌半径照旧 4.2，只打贴脸的；被打不还手才怪，正常还手；
- 遇建筑就拆（现有 `nearestHostile` 的权重排序直接复用：塔权重 4、其它 1.5）；
- 不吃后勤（`breadCost: 0`）、不占人口（`fromBarracks: true`）、不产金、不进手牌。

这样怪和 1v1 的红方兵**用的是同一套 `tickUnits`**，只换"往哪走"的目标解析 ——
不需要维护第二份兵的行为。

## 5. 波次与胜负

```ts
// src/arena/pve/waves.ts
interface WaveSpawn { unitId: string; count: number; row?: number }
interface Wave { at: number; lane?: [number, number]; spawns: WaveSpawn[]; elite?: boolean }
```

- `at` = 开打后第几秒。**第一波 20 秒**（开局 8 金 + 20 秒攒 10 金 = 18 金，
  够立第一栋楼再搭一队兵）；前两波隔 50~60 秒；末三批 130 / 142 / 154 每 12 秒一压。
- 波次表在 `levels.ts`，垂直切片先做 **1 关 5 波**（`outpost`，显示为 1/5 … 5/5）。
- 判据（PVE 专用，**不碰 1v1 的加时/积分**），三个出口：

  ```ts
  if (!this.coreOf('blue')) return this.finish('lose', 'core');   // ① 大本营被打穿
  if (this.elapsed >= s.level.seconds) return this.finish('win', 'waves');  // ② 守满时限
  if (s.next < s.level.waves.length) return;                      // 波次没出完 → 继续
  for (const u of this.units) if (u.side === 'red' && u.hp > 0) return;
  this.finish('win', 'waves');                                    // ③ 清光全部怪
  ```

- **为什么必须有时限（`seconds: 300`）**：塔防的残局会僵持 —— 一只石怪拆一栋 520 血的塔
  要 137 秒，实测最后一波 154 秒就出完，却拖到 **376 秒**还在磨。5 分钟是塔防的常识上限，
  也让"守多久"本身成为一条明确的胜利条件。石怪随即换成兽人（8.8 dps vs 3.8）。
- 击杀统计（`pve.slain`）挂在**血量跨过 0 的那一刻**，不是挂在单位数组的 filter 上 ——
  后者会漏数（实测 70 只只数到 10，尸体清掉就查不到了）。
- `outcomeReason` 加 `'waves'`（守住）与 `'core'`（被打穿）两种。

### 5.1 当前平衡读数（2026-11-07 定稿）

托管蓝方、12 个 seed、同一关卡：

```
seed=1        win/waves  t=300s core=1180     seed=7        win/waves  t=237s core=399
seed=2        win/waves  t=227s core=580      seed=8        lose/core  t=124s core=0
seed=3        win/waves  t=209s core=1165     seed=20261027 lose/core  t=185s core=0
seed=4        win/waves  t=234s core=1165     seed=111      win/waves  t=239s core=723
seed=5        win/waves  t=208s core=1200     seed=222      win/waves  t=215s core=1200
seed=6        lose/core  t=207s core=0        seed=333      lose/core  t=188s core=0
```

**胜率 8/12 · 平均大本营 634（53%）· 平均时长 214 秒（3.6 分钟）。**

判据怎么读：托管 AI 只会"按权重找地方盖 + 攒够就出兵"，不会集火、不会留兵守塔，
所以托管能过 2/3，人手打应该是"能过但不轻松"。**这个读数就是教学关的标准**，
以后再调波次就拿这张表比。

**双人同屏（同样的 12 个 seed、两人都托管）：**

| | 单人 | 双人 |
| --- | --- | --- |
| 胜率 | 8/12 | **12/12** |
| 平均大本营 | 634（53%） | **1076（90%）** |
| 平均时长 | 214s | 251s |

双人偏简单（双倍经济、双倍决策频率），**刻意不调**：

1. 这是第一关教学关，合作模式本来就该让人过得爽；
2. 托管每 2.5 秒想一次，两个人托管 = 决策频率翻倍，这是 API 托管特有的优势；
   真人两个人在**同一块屏**上抢操作，效率远低于双托管 —— 12/12 不代表真人也能过；
3. 要加大难度应该是**加第二关**，不是把第一关调难（调难会连带单人也变难，
   因为波次表是同一张）。

调平衡时的三次大摆动（记下来别再走一遍）：

| 改法 | 结果 | 教训 |
| --- | --- | --- |
| 12 / 40 / 75 三波 | 托管满血通关 | 波数少于 3 就没有"撑"的感觉 |
| 60×32 + 全部集中一路 | 12 局全败 | 单点压力会瞬间塌，必须按行散开 |
| 20 / 75 / 140 三波 | 又满血通关 | 只加厚度不加批次，会被塔叠加清干净 |

**红线**：不许用"加金币 / 加双倍金"来救节奏 —— 那会冲垮建筑配给这条主约束（见 §6）。

## 8. 踩坑清单（给以后改这块的自己看）

| 现象 | 真凶 | 修法 |
| --- | --- | --- |
| PVE 机位设了完全不生效（yaw 停 24、pitch 停 50、`locked=true`） | `DebugPanel` 构造末尾 `userTouched() + apply()` 把相机强拽到 `DEFAULT_SHOT` 并上锁 | 删掉；改成"打开面板时"把滑杆同步到当前机位 |
| 导演机位只在 `!locked` 时应用 | 构造参数给的初值被 `locked` 挡住 | PVE 初值从 `CameraRig` **构造参数**给，不走导演 |
| 竖屏里战场被压成横向一条、上下大片黑 | `col` 轴映射世界 x（水平），竖屏要的是纵深 | `yawFix = 270`、`pitchBias = -10`，`fitZoom` 按 `rows` 算 |
| 玩家槽化后 PVE 从 9/12 掉到 3/12 | `update()` 遍历 `['blue','red']`，PVE 里 red 回落 `players[0]` ⇒ 蓝方双份金币 | 遍历 `this.players` |
| 击杀数 70 只只数到 10 | `pve.slain` 挂在 filter 回调上，尸体被清就漏 | 挂到血量跨 0 的那一刻 |
| 金币/托管 getter 化后 35 条老测试红 | `world.gold.blue = 20` 的写入静默丢失 | `sideBridge()` 用 `defineProperty` 做 get/set 桥 |
