## ② 为什么按这条线切

**切的标准是"要不要读类的状态"**，不是"代码有多长"：

- 给参数就出 `Object3D` 的（脚手架、血条、弹丸、废墟）→ 纯函数，搬进 `visuals/`。
  它们原来散在 `ArenaApp` 末尾 340 行里，读代码的人要滚很久才发现"这不是 App 的一部分"。
- 只算数据、不碰世界的（`wishList` / `chooseCard`）→ 搬进 `ai.ts`。**这条最有价值**：
  以前"AI 怎么挑牌"只能跑 60 秒看结果，现在给一份手牌就能断言"该出第几格"。
- 类型定义 → `types.ts`。`ArenaWorld` 前 180 行全是 interface，和"每帧规则"混在一起很干扰。

**没切的部分**：`ArenaApp` 的建筑同步（`syncBuildings` 130 行）、单位同步（`syncUnits` 150 行）
留在类里。它们每一步都要读 `this.parts` / `this.buildingMeshes` / `this.rig`，
抽出去等于把类的状态摊成参数列表 —— 代码只会更长、不会更清楚。

## ③ 兼容：类型仍然能从 `ArenaWorld` 拿

`ArenaWorld.ts` 顶部留了一段 re-export：

```ts
export type { ArenaBuilding, ArenaUnit, HitKind, Side, ... } from './types';
export { statsOf } from './types';
```

定义**只有 `types.ts` 一份**，转发是为了不让 `ArenaApp` / `damage.ts` / `visuals/labels.ts`
的 import 路径全散到两个地方。如果以后发现有人在 `types.ts` 里加逻辑，就该把这行删掉。

## ④ 顺手补的锁（6 条，373 全绿）

`tests/arena.test.ts` 新增一组「AI 决策：出哪张、什么时候攒钱」：

- 场上没有民居 → 先出民居（名额排在盖新楼前面）
- 有民居没塔 → 出塔，不继续堆民居
- 建筑买不起 → **返回 null 攒钱**（不把最后 6 金花在弓箭手上）
- 军队买不起最想要的那张 → 能出什么先出什么
- 手上一张牌都没有 → 不出牌也不报错
- `wishList` 第一项永远是后勤，军队排在兵营之后

这 6 条以前只能用"跑 60 秒看出牌"间接验，现在是纯函数直断。

## ⑤ 剩下的超大文件：拆不拆

| 文件 | 行数 | 判断 |
| --- | --- | --- |
| `game/systems/Combat.ts` | **1445** | **暂不拆**。它是老模式（`/`）的战斗内核，这一版的主线在对战模式；没有新需求驱动时拆它，只是把风险摊到没有测试保护的路径上（老模式的战斗锁只有 12 条） |
| `styles/components.css` | **1333** | **暂不拆**。CSS 拆开要靠 `@import` 或构建工具串起来，收益是"找样式快一点"；现在的分界线（components / layout / arena / base）已经够用，且 `arena.css` 和 `components.css` 有互相覆盖的量，硬拆会改变层叠顺序 |
| `arena/ArenaApp.ts` | 1075 | 到边界了。类本身约 990 行 = 装配 + 输入 + 8 个 sync，再往里切会把状态摊成参数 |
| `arena/ArenaWorld.ts` | 991 | 到边界了。剩下的是"每帧规则"：建筑节拍、单位 AI、寻敌、走位、胜负。下一步要拆只能是 `tickUnits` 那一坨（约 220 行），但它读写十来个私有字段，拆了得先造一个上下文对象 |

一句话：**对战模式这两个到 1000 行左右是合理的**（一个状态机 + 一个渲染装配）；
真正超标的是 `Combat.ts`，但它是老模式的，等老模式的活儿再来动。

## ⑥ 一个观察（没改）

废墟的碎块会摊到占地外约 0.9 格（`burst = 0.6`）。贴着黄区的楼拆掉之后，
废墟会有一条压在黄线上 —— 逻辑没影响（废墟只是装饰），但截图里看得到。
要收就把 `burst` 降到 0.4，代价是废墟又变得"挤在占地里"。
