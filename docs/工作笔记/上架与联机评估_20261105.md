# 上架 TapTap + 多人联机：评估（2026-11-05）

用户："看看能不能支持多人联机，未来准备上架 TapTap 的小游戏，帮我联网评估。"

结论先放最前面：

> **上架走「H5 游戏」这条路，不走「Tap 小游戏（WebGL）」；联机技术上可行且比想象的省，但"单机改联网"会让资质重做一遍 —— 要加就第一版加。**

---

## ① TapTap 有四条路，我们只能走一条

官方文档把"在 TapTap 上跑的游戏"分成四种，四条路的文档互不通用（官方原话："读错档是返工最常见的原因"）：

| 路 | 形态 | 适合谁 | 我们能不能走 |
| --- | --- | --- | --- |
| **TapTap 制造** | UrhoX 引擎 + Lua，平台托管 | 没有编程基础 | ✗ 我们已有完整工程 |
| **Tap 小游戏（WebGL）** | Unity / Cocos Creator 导出 + 官方打包工具出 zip | 有引擎经验的团队 | ✗ 我们是 Vite + Three.js，不是 Unity/Cocos |
| **H5 游戏** | H5 形式打包，**部署在平台域名下运行** | 纯网页技术栈 | **✓ 这是我们的路** |
| APK / PC 包 | 原生客户端 | 完整手游 / PC | ✗ 没必要 |

这条判断很关键：如果照着"Tap 小游戏"的文档去接 Unity 打包工具，会白干一轮。

## ② 硬性指标对照（官方口径）

| 要求 | 官方数字 | 我们现在 |
| --- | --- | --- |
| 首包大小 | ≤ 60MB（优秀 10MB） | `dist` 整包约 **0.7MB**（three.js 493KB + 游戏代码 200KB + 素材）— 远低于红线 |
| TapTap 登录 | 包体内必须接，否则用户无法游玩 | ✗ 没接（走 H5 路线时要按 H5 的接入方式补） |
| 版号 | **无内购不需要**，但要**小游戏前置备案** | ✗ 还没备案 |
| 防沉迷 | 仅"小游戏"形态由平台默认开启；同时提供 APK 才要自己接 | 走 H5 待确认 |
| 审核时长 | 首次 1–3 天，资料更新 1 天 | — |
| 商店素材 | 9:16 竖版截图（实机画面，不能用过场动画） | ✗ 现在只有横版截图 |

**一条容易漏的**：官方 FAQ 明确写了"**如果游戏发生单机改联网、无广告改有广告等较大变动，需要按变化后的要求处理资质**"。
也就是说"先上单机、以后再加联机"= 备案要重做一次。**联机要加，就第一版加。**

## ③ 多人联机：技术上比想象的省

先做了一次体检（这条决定方案可行性）：

| 检查项 | 结果 | 意味着 |
| --- | --- | --- |
| 逻辑层是否用 `Math.random` | **0 处**（`ArenaWorld` 全走 seeded `this.rng`） | 战局可复现 |
| 主循环 | 固定步长 **20Hz**（`GameLoop.fixedDt = 1/50` 秒），渲染与逻辑分离 | 天生适合帧同步 |
| 逻辑与渲染是否分离 | `ArenaWorld` 不 import three | 服务器可以直接跑逻辑，不需要 WebGL |
| 唯一一处 `Math.random` | `ArenaApp` 的行军扬尘间隔（纯视觉） | 不影响战局 |

**两条路线：**

| | 帧同步（lockstep） | 状态同步（权威服务器） |
| --- | --- | --- |
| 服务器干什么 | 只转发输入（出牌 / 移动指令），不跑逻辑 | 跑 `ArenaWorld`，每 100ms 广播快照 |
| 带宽 | 1v1 约 **<1KB/分钟** | 约 2–4KB/秒 |
| 确定性要求 | **极高**（一处浮点分叉，两边就打出不同的仗） | 无（服务器说了算） |
| 客户端预测 | 必须做（否则有输入延迟） | 可做插值，不做也能玩 |
| 反作弊 | 弱（客户端各跑各的） | 强 |
| 我们的改造量 | **小**：输入队列 + 帧号对齐 + 断线重连 | 中：服务器工程 + 快照协议 + 客户端插值 |

**风险点（帧同步）**：JS 引擎之间 `Math.sin/atan2/hypot` 可能有 1 ulp 差异，
而这个项目里寻敌用的是 `Math.hypot`、朝向用 `Math.atan2`。3 分钟 × 20Hz = 3600 步，
1 ulp 有可能被放大成分叉。

**建议**：**先做状态同步**。理由不是"更先进"，而是：
- 我们对"服务器跑一份 `ArenaWorld`"这件事**零额外风险**（它本来就不依赖 three）；
- 不用赌浮点确定性，也不用做客户端预测和回滚；
- 1v1、几十个单位的快照，2KB/s 完全扛得住，一台 2C2G 能带几百个房间。

**如果真要帧同步**（为了带宽和"手感一致"），前置条件是：把寻敌/走位里的 `hypot/atan2`
换成整数近似或查表，并且每 5 秒做一次状态哈希校验。

**工作量粗估**（不含美术/音效）：
- 状态同步最小可玩（房间 + 匹配码 + 快照 + 断线）：**3–5 天**
- 帧同步（含确定性改造 + 预测 + 校验）：**7–10 天**，且调试成本更高

## ④ 游戏本身的问题（作为"一款要上架的游戏"看）

按"会不会卡住上架 / 会不会劝退玩家"排序：

| # | 问题 | 严重度 | 现状 |
| --- | --- | --- | --- |
| 1 | **完全没有音效** | 高 | `src/` 里零 `AudioContext`。RTS 没有打击音、没有金币声，手感少一半 |
| 2 | **没有存档 / 成长** | 高（审核点） | 每局重置。TapTap 驳回高发点里明确写着"无存档、无成长、无收集" |
| 3 | **竖屏背景全黑** | 中 | 竖屏 390×844 下，菜单背后几乎看不到战场（相机 fit 是按横版算的） |
| 4 | 只有一档难度 | 中 | AI 恒定，没有新手/普通/困难 |
| 5 | 结算太薄 | 中 | 只有"胜/负 + 再来一局"，没有拆了几栋、谁拆得多、最高连击这类可炫耀的数字 |
| 6 | 没有设置 | 低 | 音量/画质/语言都没有入口 |
| 7 | 没有埋点 | 低（运营） | 上架后看不到留存和流失点 |
| 8 | 触控未在小屏验证 | 中 | 卡牌高 60px 左右，拇指点选要真机验 |

第 1、2 条是"上架前必须解决"的；第 3 条是"这一版就能修"的。

## ⑤ 建议顺序

1. **先把当前这堆改动提交**（9 天没 commit 了，见 `2026-11-05` 的体检记录）；
2. **音效**（打击 / 开火 / 金币 / 建造完成），这是投入产出比最高的一条；
3. **竖屏适配**（相机 fit + HUD 重排），H5 用户大半是竖屏点进来的；
4. **联机**（状态同步），**和备案一起做**，别先上单机再改；
5. 存档/成长：哪怕只是"累计拆了多少栋楼"的本地记录，也比零强；
6. 最后才是商店素材（9:16 实机截图）与提审。
